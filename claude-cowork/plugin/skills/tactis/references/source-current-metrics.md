# Current metrics and finite refresh

Inspect `freshness.metric_coverage` for each requested daily metric and `available_metrics` for the fully covered fresh subset. Direct `direct_goal_metric_not_reported` means the provider returned unknown goal fields; it does not erase known spend/clicks/impressions or prove zero conversions. The combined request remains unavailable if a requested field is unknown. Request a needed primitive subset separately instead of replacing missing goal values with zero. Missing-date bounds enclose the gaps and do not mean every date between them is missing.

Direct `ad_performance` supplies native ad/group/campaign facts when the provider exposes IDs and the pinned configuration proves the exact owner. Read its fact pages and retain their clocks, currency/VAT and selected goal. `direct_ad_identity_unavailable` or `direct_ad_lineage_unproven` remains a data limitation; do not allocate campaign totals to ads. Current Metrika ad diagnostics use the explicit `cross_device_last_significant` provider model. An old `metrika_attribution_model_unproven` snapshot needs a new acquisition for a current comparison; its historical rows remain readable.

Direct `search_query` returns `data_kind="search_query_metrics"`: exact query text grouped by campaign over the selected dates, ranked by observed spend, with full-scope `summary` totals, query count and coverage. Use this page for a shortlist; do not exhaust all rows merely to calculate a denominator already in `summary`. Request another page only when the decision needs more candidates. `observed_metrics` are partial observations; only covered non-null `metrics` are period totals. Missing conversions remain unknown, and search-query totals do not prove the whole campaign ledger. Preserve campaign/query, selected goal, publication and period when comparing with existing keywords.

Direct `geography`, `demographics` and `device` return `data_kind="dimension_metrics"`: period totals per native dimension across the selected campaigns, ranked by observed spend, with a full-selection summary and campaign-day coverage. Geography uses `LocationOfPresenceId`, demographics the full `Gender`/`Age` pair, and device the exact `Device` value. A missing identity stays distinct from provider placeholders. Geographic names are display metadata: differing names for one ID produce a null consensus name and a variant count. Keep the campaign count/fingerprint and `retained_<family>_rows` population; these are not a campaign ledger. Mixed goal/counter identities leave row and summary conversions unknown. A missing city on a partial page is not proven absent or zero; page further only for observations needed by the decision. Other leaves retain `fact_rows`; daily detail uses `get_daygrain_values`. These daily families do not supply an hourly dimension.

Use for current/today status or a requested fresh provider reread. `get_current_metrics` admits/joins source collection and can refresh it; it is not a side-effect-free retained reader. If the user excludes new collection, use [retained statistics](source-history.md) and label their actual as-of/unknown current state. Reuse the selected scope. Permitted data collection does not require advertising-change consent and never authorizes an ad effect.

For an ordinary current-status question, reuse the known project/account/source scope and call `get_current_metrics` for the exact required family, metrics, dates and counter/goal. The backend joins or starts its bounded source collection and refreshes active queries every 30 minutes. Only `state="fresh"` contains current numerical data: every contributing receipt must be complete and at most 3600 seconds old. `pending`/`unavailable` describe the actual collection or coverage problem and contain no current numbers. Follow its job/next-due locator; polling does not create another acquisition. Preserve the returned query, publication/fingerprint and freshness proof; page its `data` using the same query and next offset. Backend activity expires after two hours without a demand; the next request activates an expired query. Cancellation stays separate from ordinary polling. This statistics read creates no advertising operation and requires no additional advertising consent.

A short “continue” or explanation in the same chat reuses the just-read fresh response for the same scope and window; it does not request a refresh by itself. Rephrasing or showing that observation needs neither a clock lookup nor another status read. Read again when the user requests updated facts, a relevant due event is known to have arrived, or changed data, context or access makes the previous response insufficient. For pending work, wait for its returned job due time before another status read and retain the same query/command identity. Unchanged waiting does not need a Work or task.

For a historical backfill use `refresh_mode="once"`, unless a suitable retained publication already exists. It collects the exact supported family/window once and stops its backend schedule after completion; polling, restart, expiry or a changed source head does not silently start another acquisition. Its accepted finite job has a fixed 24-hour deadline and continues without an open chat; the two-hour activity rule above applies to active queries. Polling never extends the finite deadline. A new explicit reread uses a new stable `force_nonce`. After the one-hour current-data horizon, open the labelled `retained_historical_reference` through its exact historical readers; old history does not become current merely because it was read. Ordinary active queries omit `refresh_mode`.

For “year plus today”, reuse or capture the historical part once and keep a separate active query for today or the needed short correction window. Make the windows disjoint, preserve each publication's as-of and event/currency/population identity, and avoid recurring full-year acquisition for ordinary daily questions. Backend readers aggregate each frozen publication; the current API returns history and the fresh tail as separate slices. Their combination is a mixed-time observation, not a fully fresh annual publication. A provider can correct past days; the correction window and any requested historical reread must remain explicit rather than assuming that yesterday or a fixed three-day cutoff is permanently settled.

Keep the returned population and limitations with the numbers. Campaign families cover selected currently authorized campaigns; they do not prove every campaign that existed historically. Counter families cover the authorized counter. Dates can span a supported year without a product 60-day cap and can include source-local today. Preserve `calendar.finality`, its frozen `provisional_date`, reporting timezone and actual source receipt time. Say “Сегодня, предварительно; получено от провайдера <timestamp>” for an unfinished day. A publication remains preliminary after midnight until a new actual acquisition; calendar closure never promises settled attribution or no later corrections. Recent acquisition does not bound the provider's own processing delay; unknown lag is not zero. A new manual request for an actual reread may set a stable `force_nonce`; preserve it on every poll/page so those calls join the same acquisition. Ordinary reads omit it. Resume an explicitly cancelled query only when the user requests resumption, using `resume_cancelled=true` with the same query.

Reuse known freshness evidence or call `get_source_freshness` when freshness matters and that evidence is missing or stale. The ordinary MCP brief does not load source freshness. The backend refreshes current configuration and all 60 days of campaign primitives every 30 minutes; an actual observation age over 3600 seconds is stale. `data_as_of` comes from source receipts, `captured_at` dates the saved publication, and `calendar_through` is its last completed day. A newly saved wrapper does not refresh reused facts. Explain stale/partial/pending collection with its actual status; do not describe the previous publication as current or fill missing values with zero. This proof does not cover intraday figures, provider processing delays, conversion statistics, CRM or immutable historical analyses. Their own receipts and coverage remain authoritative.

Campaign and search-query metric items carry `campaign_name` from the exact pinned configuration inventory; a null name is unknown, not an invented label. Dimension totals describe the selected campaign scope collectively. An ordinary “how is advertising doing?” question does not need a configuration catalog read just for names. For configuration status or settings beyond the metric result, use `list_configuration_campaigns(summary=true)` with its existing publication/scope and pagination. It is an explicitly labelled projection with original artifact locators, family states and observed counts, not live provider status or a complete child inventory. Read the exact `get_configuration_campaign` family for the needed settings or rows. Omitted/false summary preserves the full catalog.

For a targeted traffic question, `get_current_metrics` can select Direct `keyword_performance`, `geography` or `demographics` without collecting unrelated families. Its normal scope, provider retention, finite budget, current/pending state and immutable readback remain authoritative. When a full rolling diagnostic capture actually needs these reports, use the sorted unique `additional_direct_families` selector in `capture_daygrain`; omission preserves its existing collection volume. Read their exact values/dimensions and metric acquisition times. Criteria, location and gender/age are separate provider populations; do not assign campaign differences to an unreported segment or treat missing rows as zero.

For an existing immutable publication, use [historical metric readers](source-history.md#retained-statistics-and-coverage). For a real missing connection use [connector setup](connector-setup.md); do not load setup or full account inventory just to read an available metric.
