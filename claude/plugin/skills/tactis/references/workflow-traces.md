# Three short worked routes

These are **synthetic instructional traces**, not executed acceptance, client evidence or copyable complete mutation payloads. A/B/C are local labels, and “returned” means a value from the actual named reader. IDs, fingerprints, versions, dates and hashes must come from that run. The traces show the ordinary next result; use only its relevant recipe.

## 1. Advertising declined → a saved priority → another host

**Request:** «В этом кабинете стало меньше заявок. Что первым проверить?»

1. Reuse the selected project/account; `get_project_brief` and exact relevant `get_work_session` recover context. Here the selected goal's business correspondence is unconfirmed, so call it the measured technical event.
2. `get_current_daygrain` supplies one retained statistics ID. Two `get_campaign_metrics` reads on that **same Daygrain** ID compare completed equal windows and the same source/goal/attribution. Follow their pages. Suppose covered events for A are 30→15, B 20→15, C 10→15: total −15; A is the main known negative contributor (−15), B −5, C offsets +5. These numbers do not establish lost qualified leads or causation.
3. Inspect only the relevant evidence: current Configuration locator → `get_configuration_campaign` for A's campaign state, or its exact dossier query family for an intent question. A stopped state today does not establish the historical stop date/cause. Return the finding, one supported check and the business-event unknown.
4. `record_work_session(kind="assessment")` saves the compact diagnosis, actual Daygrain/configuration typed refs, limitations and next step; exact `get_work_session` confirms it. Intermediate task work uses keep_pending. In ZCode or Codex later, authenticate normally and read the **same exact Work**, recover that next step and check only its changed dependencies. A new chat does not regenerate a different conclusion or share credentials.

## 2. Exact negative change → lost response → same Application

**Request:** remove only an irrelevant repair intent from an existing search group, preserving the other negatives. The example is conditional on read offer/query evidence, not a universal blacklist.

1. The complete before-set and useful intents come from the pinned configuration/dossier readers. `get_operations_catalog(operation="negative_keywords", include_schema=true)` gives the precise replacement shape. `prepare_native_scope` and `get_native_configuration` supply the selected ancestry and current object_id/version. Actual `get_analysis_campaign_reference` supplies the matching analysis context; unsupported/missing proof leaves a proposal material, not an executable change.
2. `propose_operations` freezes the complete exact replacement set under the original command_key, analysis_basis and confirmed context versions. `get_operations_plan` supplies Plan ID/digest and before/after. Explain the useful-demand risk; take the person's exact choice already given or obtain it.
3. `execute_operations(project_id, plan_id, digest)` loses its response. Keep the identity. If the original plan's proposal.command_key and digest are known, `replay_operations(project_id, plan_id, command_key, digest)` returns the existing Application without dispatch. If identity is incomplete, use scoped `get_operations_work(collection="applications", plan_id=...)` then `get_operations_application`; do not guess a key or create a replacement plan.
4. Queued means admitted; applied plus per-object readback confirms the technical change. Unknown/partial/recovery_required remains unresolved. Save the actual status and exact next read in Work. Application.measurement_id → `get_native_measurement` fixes the real window/maturity; only its actual latest outcome is read later. No future outcome or causal savings is invented to finish the trace.

## 3. Weekly review → durable result → delivery acknowledgement

**Request:** a weekly note and next step for an existing client. The host already has one authorized recurrence; the trace does not create another.

1. Read the original selected Work/criterion. **Only for an existing due Tactis task**, `get_proactive_delivery_policy` → `claim_proactive_delivery` first yields the actual task/delivery/lease. Pin the completed compatible period. `get_campaign_metrics(aggregation="calendar_week")` supplies relevant family rows; clipped edge weeks are labelled, pages completed and incompatible events kept separate. [Marketing review](marketing-review.md#report-for-a-decision) connects facts to the recipient's decision.
2. Deliver a short note: scope/units/coverage, useful change, exact prior Application/measurement state, up to three priorities and one next check. A stable week still gets the requested note; no change does not require an invented incident. `record_work_session(kind="weekly_review")` → exact `get_work_session` retains it.
3. **Only for that claimed due task:** the Work must be linked to its task_id with `task_resolution="complete"` after achieving its required result; `ack_proactive_delivery` uses exact delivery_id/lease_token/Work ID → `get_proactive_delivery` confirms delivered. Intermediate output uses keep_pending and is not acked. An ordinary weekly note needs no claim/ack. Delivery acknowledgement is separate from human visibility and business effect.
4. In another authorized host, read the original criterion and this same Work and resume its useful next result. The original native schedule/lease does not transfer with Work. Pending maturity stays pending; calendar time or a saved note cannot prove completed business judgement.
