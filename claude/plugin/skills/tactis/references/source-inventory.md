# Account inventory, analysis and dossiers

Use for a full account assessment or the particular inventory/analysis/dossier gap, not a simple text draft or an ordinary metrics question. For a narrow question prefer [current metrics](source-current-metrics.md) or [exact retained evidence](source-history.md).

## Configuration and source scope

Use this procedure for a connected account's advertising assessment or necessary source checks while resuming. Start a relevant resumed turn with [durable continuation](durable-continuation.md); apply this full inventory procedure only when the question or material evidence gap calls for it. Resolve the user's authorized project/account and source binding or full-account read grant through current server ports. Provider tokens stay in Ads Core. The agent supplies references, not credentials or a fabricated campaign list.

Reuse the known current source scope and locators. Read `get_account_read_grant` only when the connected account's source metadata/proof is missing or has changed; its source grant ID is the source_binding_id of the modern read path. `list_account_read_campaigns` pages the confirmed inventory. Preserve the lineage and original publications of retained historical connections; they do not substitute for the current account read grant. A source read grant permits collection. Before an advertising change, ask for the user's choice in chat; provider permissions and exact server write guards remain separate.

Read `get_current_configuration` with the exact account/source reference. If a load is pending, `list_configuration_jobs` or `get_configuration_job` returns its durable state and due time; installation and loading can proceed independently. Use `capture_configuration` only when a fresh authorized read is needed. Preserve the command key on retry. Loading is a read job, not a campaign write or a request for another OAuth consent.

Pin the returned publication ID and manifest fingerprint. `list_configuration_campaigns(summary=true)` returns a bounded ordered status/coverage catalog with full total and next_offset; use the full mode when its campaign settings are needed. Follow its pages until the intended inventory is covered. `get_configuration_campaign` pages the campaign, groups, ads, keywords, audience targets or modifiers; `get_configuration_retargeting_lists` pages the account catalog. An unavailable family is unknown. A verified complete empty family is empty. Inventory completeness does not prove each child family complete. Query text is not keyword identity: retain native campaign/group/ad/keyword lineage.

The `ads` family retains full referenced assets in `referenced_callouts` and `referenced_sitelink_set`: their native IDs, exact text/URLs/descriptions, binding and available provider moderation. Callout moderation belongs to the extension; sitelink moderation belongs to its binding on each ad. Check each enrichment's `state` and reason before claiming completeness. Missing/unavailable is not an empty list. Shared IDs on the actual returned ad rows prove those relationships; one page does not prove every ad in the account using an asset. Read the remaining relevant pages for that claim. A reused campaign snapshot does not alone prove fresh callout status.

For statistics, reuse a known compatible retained **Daygrain** publication; otherwise read `get_current_daygrain` for the needed profile and pin its separate statistics ID/fingerprint. If collection is already pending, follow its actual `list_daygrain_jobs` / `get_daygrain_job` locator and due time. When the required short-window D3 is absent or needs an authorized refresh, `capture_daygrain` uses the verified inventory publication and server-owned window policy; retain one command key and frozen inputs on retry, then follow `get_daygrain_job` to its completed publication. Do not use the job ID as evidence. An explicit no-collection instruction permits retained reads only: preserve the gap and useful supported result instead of admitting a capture. A read grant does not override that instruction.

Read `get_campaign_metrics` with that exact Daygrain ID and required window/source. Its campaign families are `campaign_performance`, `metrika_counter_visits` and `metrika_exact_goal`. For Direct `search_query`, `geography`, `demographics` or `device` period totals, use the same reader with `aggregation="total"`: a bounded ranked page includes the full selected-scope summary and coverage. Dimensions aggregate across the selected campaigns; query rows retain campaign/query identity. Preserve the returned population and native identities; these leaf totals do not replace the campaign ledger. Read more pages only for observations the decision needs, not to recalculate a summary already returned. For placement or richer criterion observations, reuse the matching Dossier and read only the needed `get_campaign_dossier(family=..., limit, offset)` pages; prepare matching Analysis/Dossier below only when that material is needed and absent. `get_daygrain_values` pages the whole frozen publication without window/source/family filters: do not scan every family to answer one narrow family question. Preserve the reader's actual retained window and partial coverage; no route supplies missing dates. Use [retained coverage readers](source-history.md#retained-statistics-and-coverage) for the detailed family contract and relevant missing proof. Follow pages for the claimed scope; incomplete/null is unknown, not zero. `capture_analysis` below consumes compatible pinned evidence, never a pending job. Discovering a current head does not replace a saved historical basis or refresh its original as-of. Longer archives and explicit late-data rereads use [their separate path](#longer-historical-acquisition).

The cabinet counter/goal pair is optional additional evidence. Read the publication's campaign counter and goal bindings: campaigns may use different counters and events. The server collects goals only from counters linked by the current Direct configuration. Catalog-discovered goals and the cabinet's extra pair are not automatically a campaign's primary event. Provider labels explain technical events; they do not confirm business goals or memory. Direct strategy goals such as engaged sessions are not ordinary Metrika goals.

For each available linked counter, use the actual `get_campaign_metrics` schema with source `metrika`, family `metrika_counter_visits` and that counter to read visits without a selected goal. Read `metrika_exact_goal` separately for relevant exact counter/goal pairs. Preserve each event's scope and origin; do not sum overlapping goal counts as total leads or silently substitute one event for another. If catalog enrichment is pending, use available Direct facts and explain which Metrika evidence is still loading. Do not ask the user to select a global pair before giving the supported assessment.

An Analysis row does not project counter visits; their absence there does not prove they are missing from Daygrain. Read the counter-visits family only when this question needs it. For a standalone counter, `get_metrika_goal_catalog` supplies automatically refreshed goal definitions, active/archive state, changed definitions and selected-goal status. Its backend cadence is 30 minutes with a one-hour freshness limit; the chat does not maintain that schedule. Use exact event definitions, not display names, to distinguish a registration-page visit from completed registration. An archived or changed selection is not silently replaced with another goal. An explicitly chosen goal can be read through `capture_page_observation` with that catalog's `goal_catalog_publication_id`; a visits-only read cannot replace unavailable conversions. For Direct-linked counter definitions, `get_audience_sources` requires the actually selected, authorized project counter and 1–10 exact goal IDs per request; a counter found in campaign configuration alone does not satisfy that selection. On `product_selected_counter_required` or another counter-selection rejection, stop remaining goal batches until that prerequisite changes and use [conditional recovery](session-recovery.md#access-or-connection). Continue supported retained visits/goal metrics independently; do not select a counter or change a connection merely to make the reader pass. A `landing_cta_click` remains a technical click unless completion and linkage are established.

## Analysis, dossiers and hypotheses

For a search-query shortlist or monthly spend/clicks/impressions totals, use the exact retained `get_campaign_metrics(family="search_query")` page and its full-scope summary, or the corresponding current-metrics result. An existing matching Dossier can supply richer observations; a new Analysis/Dossier is not a prerequisite for query totals. Preserve unknown conversions and the difference between search-query population and the campaign ledger.

For economics, call `capture_analysis` over an exact completed-day window and one explicitly chosen conversion source. Use its full successful manifest, fingerprint, account/comparison scope and limits; `get_analysis_manifest` restores it later or resolves an unknown/incomplete response. Read all needed `list_analysis_campaigns` pages. Different goal denominators cannot become an account lead total. `get_configuration_refresh` and `get_daygrain_refresh` distinguish paused, pending and due collection; a frozen inventory has its own capture identity even when daily statistics advance.

Prepare `capture_dossiers` from that analysis. Pin `get_dossier_manifest` and page `list_dossier_campaigns` when their locators are not already known. With the exact Dossier/campaign locator, `get_campaign_dossier` without family exposes campaign metadata, family counts and coverage when needed; passing `family` reads its bounded `limit`/`offset` pages directly. Follow needed pages without a compulsory metadata read. `capture_candidates` prepares independent mechanical suggestions. `get_candidate_family` without family reads the Candidate manifest when needed; passing a selected family reads its pages directly with the same exact Candidate publication ID and any known `expected_fingerprint`. Preserve coverage and follow returned pagination. A failed or unavailable family leaves useful siblings readable. Candidates do not replace full observations or grant an action permission.

`capture_dossiers` admits durable local compute and can return a `dossier_job_` ID. Read `get_dossier_manifest(publication_id=<that job id>)` after its retry_after_ms until it returns the completed publication. A job ID is not an evidence publication and must not enter foundation_refs. Only the final publication ID/fingerprint can support campaign readers, candidates or Work. Retry a lost admission response with exactly the same command key and frozen inputs; do not create another job.

Record the assessment and remaining semantic tasks with actual immutable references. A daily statistics publication or a successful loading job is not an advertising effect or a mature experiment. Execution and reports consume only the reference types accepted by their current typed schemas.

Save portable work with the current `record_work_session` schema: foundation_refs carry each immutable publication ID, account and fingerprint. The versioned assessment links its exact analysis; hypotheses also link the exact dossier publication and each campaign dossier fingerprint. Read a campaign dossier/reference before inventing a subject. The owner validates full evidence, typed action parameters and continuation conditions. A no_action assessment requires an explicit revisit_event or aware revisit_at. These external interpretations do not automatically confirm business memory or goals.

For an `act` hypothesis saved in external work, supply a typed `action_intent` with exact observed subject and parameters. A mechanical candidate informs that choice; its `candidate_ref` alone is not a validated draft or an executable intention. Record expected benefit, uncertainty, possible harm, evaluation, dependencies and reconsideration without claiming an observed benefit.

## At the next action or report

A provider change uses [current actions](current-actions.md), including exact native scope/current object versions and unknown-effect recovery. A campaign uses [campaign launch](campaign-launch.md) for Creator money/measurement prerequisites. A requested private full-account HTML/PDF report uses [the report procedure](mvp-workflow.md#frozen-measurements-and-private-reports), with the exact saved Work/Analysis. These are later stages, not inventory-read prerequisites.

For an exact existing-object proposal, `prepare_native_scope` pins at most ten selected native campaigns and their requested child ancestry. Read `get_native_configuration` for the pinned native family and its `current_provider_state.objects`. Use the returned current `object_id` and `version` as the proposal's `expected_version`; never invent a version from a publication ID or an empty legacy map. Only explicitly selected child targets appear in that current operation view. An unavailable operation shape retains readable D1 evidence but provides no executable before state. Use only actual provider operations and the typed proposal's analysis_basis; the backend resolves its selected facts without relabelling an analysis as data.1. Unknown or unsupported writes need a typed task or continuation. Provider readback confirms an applied technical effect; it does not confirm numerical marketing benefit.

For a requested edit of existing ResponsiveAds, read `get_operations_catalog(operation="ad_update", include_schema=true)`. Select the exact ad targets in `prepare_native_scope`, then use `get_native_configuration(family="ads", operation="ad_update")`: each `current_provider_state.objects` row pairs its current `version` with `data.editable_content`, `native` and `native_assets` from the same observation. Use that version as `expected_ad_version` and that content for the edit, rather than combining an older retained D1 copy with a fresh version. The campaign's `expected_version` comes from its own current native view. Read the exact retained landing evidence first. Propose only `ad_update` operations in this plan, with `landing_source` and a `patch` containing only requested replacements. Omitted fields are preserved; `titles`/`texts` replace their complete arrays, so retain unedited variants. Explicit `sitelinks=[]` or `callouts=[]` detaches all such assets from that selected ad. Do not supply null for omission or silently shorten text.

Direct shared sitelink sets and callouts are immutable. The exact plan creates replacement assets where needed and rebinds only the selected existing ad IDs; it does not edit/delete the old shared asset or change other ads. Show the plan's before/after and apply within the user's existing exact authorization through `execute_operations`, then read the same Application's per-object result. The writer rechecks current content and binding before dispatch; Direct provides no atomic compare-and-swap, so readback must also match the complete copy, preserved fields and proven new asset IDs. An unknown asset-creation result cannot authorize another add or a guessed ID. This edit does not submit moderation, start delivery or change money. Applied configuration is distinct from accepted moderation and actual serving; report their actual states separately.

The retained landing must match the resulting ad's exact destination even when `href` is omitted from the patch. Do not use an unrelated same-account landing to justify a text or asset edit. A BusinessId-only ad without a proven HTTP(S) destination is not editable through this path unless the requested patch supplies that source-backed destination.

For a new campaign, request `prepare_native_scope` with `mode=creator_account` and an empty campaign_native_ids list. This verifies the current account and grants no authority over existing campaigns. The new draft uses an explicit supported strategy; a paid flight additionally requires its exact finite money policy. New ads cite `landing_source` with the exact retained artifact ID, fingerprint and selected span references; generic evidence IDs or a caller's authorship label cannot substitute for that source. Creation, moderation and paid launch have separate exact operations; reuse one explicit user instruction when it already covers those stages and financial bounds.

The current paused Creator draft does not choose a counter or goal. Conversion, CPA or qualified-lead measurement and TARGET_CPA require their explicit counter/goal prerequisites and cannot inherit the first available event. MAX_CLICKS can launch with technical/serving verification without a conversion goal or numerical spend target. An explicitly chosen spend target observes spending and does not measure leads. Where goal setup is required, reuse the user's applicable authorized choice, verify its readback and refresh the analysis baseline. Paid launch requires accepted moderation, current funding, the finite money policy and the exact user-authorized operation. Missing conversion prerequisites leave read-only analysis and the paused technical draft available.

Use `create_analysis_report` with the saved work session and its exact analysis for a private full-account HTML/PDF overview or audit. For launch, name the exact Application and cite its frozen native measurement when present; pending measurement is valid, and a technical draft has no numerical measurement ID. Experiment requires the saved native outcome and its exact subsequent analysis with matching frozen window and fingerprints. Save native_measurement/native_outcome references in Work alongside that analysis before requesting these reports. Monetary fields retain their own currency and VAT basis; report.3 does not fabricate a truncated campaign ID list. Read the saved report.3 metadata and authenticated links through `get_client_report`; retained historical reports keep their original schema and evidence.


For native scoped proposals, take expected_version from `get_native_configuration.current_provider_state.objects`. `get_provider_state` exposes the legacy map projection: its object versions and native scoped object-head versions have separate authority and may differ. Never replace one with the other or increase a number to make an operation pass.


## Longer historical acquisition

For an annual or other longer analysis, admit `capture_daygrain` with paired `historical_start`/`historical_end` and the verified inventory publication. There is no 60- or 90-day product cap on this archive; Direct's retention and the returned job's provider-unit/attempt budgets apply. The current profile collects daily spend/clicks/impressions for the pinned selected campaign population; it does not establish every campaign that existed historically or goal conversions. Read the job through completion, pin its separate immutable publication, and use `aggregation="calendar_month"` or `"total"` with normal pagination. The archive does not move either current head. `historical_refresh=true` requests actual rereading instead of reusing an earlier archive. `cancel_daygrain_job` retains completed parts; a new command with `resume_from_intent_id` resumes the same frozen source/calendar. Preserve the returned population, limitations and original source timestamps.

`list_daygrain_jobs` and `get_daygrain_job` preserve asynchronous report work and exact retry due times. A long provider wait does not imply revoked access. `capture_daygrain` requests the server-owned window policy under a verified inventory publication; do not invent per-request IDs or enlarge an old grant. For a user checking late conversions or changed results, pass paired `refresh_start`/`refresh_end` within the retained complete-day window to reread that period on the same source. Pin the new publication after the job completes. Metric `coverage[metric].data_as_of` shows when the needed covered facts were actually acquired; a newer manifest can reuse older facts. Keep partial useful results and the missing families visible.
