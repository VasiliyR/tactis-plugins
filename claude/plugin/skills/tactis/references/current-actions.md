# Current account and action paths

Use the actual current tools and operation schema. Native campaign, group, ad and keyword IDs are decimal strings on the MCP wire. Preserve every digit; never convert them to JavaScript numbers. Owner fingerprints and immutable receipts retain their original representation; do not recompute their identities from a reformatted display response.

For a connected diagnosis → selected improvement or SEARCH draft → status/result return, use [the Ads workflow](ads-workflow.md). It supports both independent entry branches and reuses the exact action/recovery procedures below.

## How is my advertising doing?

Use [session entry](session-entry.md) for the client and [addressed foundation reads](source-current-metrics.md) for an ordinary status question. A full inventory, landing inference or current Ads action is needed only when the user's task or a relevant evidence gap calls for it. Save a substantive result through [durable continuation](durable-continuation.md); ordinary Work remains supported even when the current-head feature is absent.

These sources assemble a schema-valid proposal; current state still decides admission. After freeze/read, preserve **chat-choice → exact execute → per-object readback** under [shared gates](invariants.md).

Read the exact existing group, keywords, negatives and relevant ads, completing every needed page. Pin fresh native scope and current object versions for the objects to be changed. A multi-title ad can be unsupported while a group-level negative change is supported; inspect per-object availability rather than treating every configuration family as writable. Do not flatten an unsupported ad to a single title or infer a writable version from a D1 fingerprint.

The catalog's `write_readiness` describes server/connection configuration, separately from object shape and the user's choice in chat. Its `legacy_connection_writes_enabled` flag concerns the old unscoped path; it is not the authority for a modern native-scoped operation. An operation-specific refusal remains binding even when `live_writes_enabled=true`.

Work access does not prove permission to freeze an Ads plan. For a refused proposal retain the useful draft and the returned reason: project/account access, scope, role or expired subscription may need the corresponding human setting. An unspecified `workspace_authorization_denied` leaves the particular cause unknown; do not widen permissions or bypass it through another path.

`get_operations_catalog` defaults to compact capabilities and readiness. The `propose_operations` declaration lists operation names and common fields compactly. When the selected operation's shape is unknown, pass its operation name and include_schema=true; other operations are excluded from that schema, while unsupported refinements and money/scope limits remain binding. Reuse an already known payload without another contract read. Do not request a whole catalog schema or infer that an advertised operation supports every provider object.

`get_operations_work` pages default to ten rows per collection; its maximum is 50, and requests above ten require one collection. Reuse the default for exact-plan recovery. A byte-limited page may include fewer rows than requested and reports page_limited_by with the actual next_offset. If an aggregate page gives zero rows for a collection, read that collection at its unchanged offset. Recovery task title/description are bounded and explicitly mark truncation; retain the task and parent plan/Application IDs even before Workspace delivery. These Ads pages are separate from Workspace `get_work_session` collections.

For modern operations, supply `analysis_basis` with the exact current analysis publication ID/fingerprint and native scope proof ID when required by the actual tool schema. Do not fabricate a data.1 snapshot or old binding as `facts_id`. Preserve unchanged keyword/negative sets under replacement semantics. Prepare a PAUSED ad variant where supported. Freeze the proposal with `propose_operations`; its full successful receipt already contains the immutable Plan ID, digest and before/after. Use `get_operations_plan` for later restoration or an unresolved/incomplete response with a known plan ID. Show the exact change, consequences and limits in chat. A returned `next_action` is navigation, not execution authority; a `preparation_only` plan remains non-executable. Reuse the user's existing authorization when it covers this action, objects and money bounds; ask and wait only for a missing or materially changed choice. Then use `execute_operations` with the saved plan ID and digest. Inspect Application and readback afterwards; never blindly retry an uncertain effect.

### Recover a lost execution response

Keep the original project, plan ID, digest and the Plan's original `proposal.command_key`. When all are known, call **`replay_operations(project_id, plan_id, command_key, digest)` first**: it returns an already saved Application and never dispatches a new effect. Its command_key is the original proposal's, not a new retry label, host run ID or guessed value. If it reports no existing execution or cannot be read, do not infer that nothing was accepted; continue the exact scoped lookup below and retain an unresolved state.

`execute_operations` can also recover its exact already admitted Application, but it is an execution entrypoint and must not be called as discovery when admission is unproved. Read/replay needs no new action consent; reuse the original exact choice. `queued` proves durable acceptance, while only `applied` with its per-object receipt/readback proves the provider effect. `unknown`, `partial` and `recovery_required` need reconciliation; none proves advertising benefit.

An explicit provider refusal is not a timeout. Preserve its code, safe message/details and Request ID, and report the actual Application state. If that state still requires recovery, use its existing recovery path; neither a readable refusal nor an empty inventory authorizes another dispatch. A generic permission code alone does not prove which role or connection setting caused it. Use the supported owner/admin correction for the stated prerequisite, without changing credentials or creating a replacement command key.

If the tool returns `operation_execution_outcome_unknown`, `ads_unavailable` or loses its response entirely, read `get_operations_work` with the exact project and plan_id and collection=applications, then read the returned ID with `get_operations_application`. Work returns paged summaries; follow the selected collection's next_offset when needed, and use existing plan/Application readers for full details. An unfiltered first page cannot prove no matching Application exists. Unrelated fact retry reads are optional and need their own bounded limit/offset; current native source jobs use list_daygrain_jobs/get_daygrain_job. If no matching Application is visible after the exact scoped read, the reader fails, or access is lost, report that verification is pending or forbidden; do not infer that nothing was accepted. Do not create a replacement plan, change command identity or blindly repeat execution. Reuse the user's existing choice for that exact plan; a recovered read requires no new consent.

For example, after consenting to one exact negative-keyword change the user sees a timeout: say “The execution response was lost; I will check the same plan.” A recovered `queued` means “Accepted, awaiting execution”; a proven `applied` means “The change is confirmed”; an unavailable read means “The state is still unknown.” Preserve the original references and next read in Work using [durable continuation](durable-continuation.md), retaining its committed saved receipt. On “What happened to that cleanup?” read those same references rather than propose the change again. A measurement still waiting for its frozen window is normal and does not block recovery acceptance; evaluate advertising outcomes later.

## Create a campaign from a domain

Fetch a bounded landing document and author a useful draft from its evidence. A concrete draft uses the known task purpose without a separate goal agreement. Missing confirmed geography may remain a clearly labelled assumption for draft copy; it is resolved before an executable plan. Budget, horizon and agreed business purpose constrain paid launch. A technical MAX_CLICKS verification follows [launch prerequisites](campaign-launch.md#resolve-financial-and-measurement-prerequisites-before-a-plan) and does not supply a business target. Reuse known answers rather than adding another preliminary questionnaire.

Use the exact `final_url` exposed by the pinned landing manifest as copy.url. The current `creative_landing_changed` error identifies `reason=ad_destination_differs_from_retained_landing`, the URL field and safe expected final_url; it does not prove the page text changed. URI origin/default-port/root normalization is bounded; path, query and fragment retain their selected identity. Read the pinned manifest and correct the mismatched input only for the intended same destination. A different destination needs its own exact source and visible chosen material; a new capture is useful only when that evidence is needed.

In each creative's `evidence_ids`, use retained evidence object IDs accepted by the exact schema, such as the pinned `landing_source.artifact_id`; D7 span references belong only in `landing_source.evidence_refs`. Do not put span references or an Analysis publication ID into the legacy evidence-object list. A modern `analysis_basis` remains separate. For `evidence_not_found`, correct the source locator from the retained manifest; changing permissions or recapturing the same page cannot repair a wrong object ID.

Use `creator_account` native scope and a current compatible analysis basis. Create only the graph declared by the operation schema, in PAUSED state. If the creator schema cannot include negatives, make their separate exact group change visible after creation/readback; do not claim they were included. Read exact new IDs and graph state. Creation, moderation and finite paid launch each need an exact operation covered by the user's choice; one explicit instruction may already authorize all three within its bounds. Configuration readiness and a preview do not prove an applied effect; the user's choice does not prove provider readback.

Follow [the complete launch recipe](campaign-launch.md) for offer → supported SEARCH material → actual PAUSED creation/readback → separate moderation and finite launch → saved observation. Native `create_campaign` freezes a finite budget with verified VAT. The current `direct_custom_period` supports one to ninety days without a mandatory percentage reserve; PAUSED creation accepts explicit unknown funding and future start dates. Paid launch has its own current funding checks.
