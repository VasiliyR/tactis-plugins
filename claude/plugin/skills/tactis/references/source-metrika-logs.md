# Metrika Logs and whole-counter reconciliation

Use for raw visit/goal evidence or an exact whole-counter reconciliation, not ordinary ad copy or an aggregate campaign status.

For actual raw/session evidence, `list_metrika_log_exports` lists already prepared Logs API exports for one exact connected standalone counter. Prefer an existing compatible processed export. `get_metrika_log_export_summary` privately reads every original part once, verifies schema/keys/bytes, retains encrypted originals and returns daily aggregates with hashes and coverage. Follow its exact `next_offset` with `publication_id`; pages do not redownload provider data. Raw visitors, client IDs and contact data never belong in chat or public materials.

For «в какие дни и часы приходят визиты и достигают цели?» use the same summary's `visit_time_distribution`: at most 168 observed weekday/hour cells, ISO Monday=1, in its verified counter `timezone`. `visits`, `goal_visits` and repeated `goal_reaches` are grouped by **visit start time**; an event after midnight remains in its originating visit's cell. They describe the whole exported visit cohort, including robot/unknown classifications, and do not establish paid campaign traffic, qualified leads or sales. The [official Logs fields](https://yandex.ru/dev/metrika/ru/logs/fields/visits) define `ym:s:dateTimeUTC` as UTC+3 despite its name; the owner converts that actual instant to the counter timezone and checks it against the visit date.

Read `status`, `timed_visits`, `unknown_visit_time_visits` and `weekday_window_days` with the cells. The last field counts calendar dates inside the exact export window; a short window can contain unequal numbers of weekdays and is not a full week's exposure. Missing/invalid visit times, a conflicting local date or an unproved counter timezone preserve independent daily counts and leave the hourly remainder unknown. `available` means the retained export visits have usable times, not complete provider processing. Zero cells are not materialized; an absent cell does not prove zero demand. Historical immutable summaries without this projection keep their original fingerprint and do not gain inferred hourly data.

Use this distribution as evidence for a schedule hypothesis, together with the actual business hours and current campaign schedule. Preserve the sample size, period and time coverage; sparse technical events do not justify cutting useful demand automatically. The [Direct Reports field list](https://yandex.ru/dev/direct/doc/ru/fields-list) has no `Hour` dimension, so this Logs projection supplies no hourly advertising spend, CPA or causal evidence for a schedule change. Follow the existing supported schedule action only for a chosen, grounded change.

If no compatible export exists, `acquire_metrika_log_export` can request fixed minimal visit/goal fields for 1–31 closed counter days through existing counter read access. For a robot-quality question on a supported Metrika Pro counter, select `include_robot_classification=true`: this adds the documented `ym:s:isRobotPro` field to that exact command, available from 2025-04-19. The base request remains useful on ordinary counters. A known rejection of the Pro field does not erase independently available visits/goals: continue the base reader without that optional field, preserving the original question and recording the robot gap. This is an analytic field selection, not another OAuth or a counter settings change.

Reuse the same `command_key` for the same exact input, including the optional robot field; at most one provider creation is admitted. Read `get_metrika_log_export_command` only at its `next_check_at`, within its fixed deadline/poll budget. `uncertain` is not permission to create again, change the field selection or attach a guessed provider request. A definite processed `request_id` can be read with the summary reader. No ad, goal, counter setting, cleanup or upload is performed by this acquisition.

For “which pages/events lead to the goal, and where does the observed path stop?”, select `source="hits"` in the same acquisition tool. The fixed native profile reads `ym:pv:visitID`, `dateTime`, `URL`, event goal IDs and page/link/download/artificial flags. Choose the useful counter/window and optional `goal_id` yourself from existing scope/catalog; traffic analysis needs no goal setup, Work or questionnaire. [Native hit visit IDs](https://yandex.ru/dev/metrika/en/logs/fields/hits) exist since 2025-10-10. Requests stay within one calendar year and 1–31 closed counter days. The existing source worker checks the definite request at its due time and retains the same export under the original current actor, source generation and 30-minute deadline. Read the command's `publication_id` when present; no extra capture is needed after a committed retained result.

The summary's `event_paths` returns aggregate sequences of second-level timestamp groups through the first observed selected goal, or the last observed event. Follow `next_offset` with the exact `publication_id`; `row_total` counts path patterns for hits, daily rows for visits. A large page uses the existing exact JSON wire-chunk response: follow its exact `next` arguments, reassemble fragments and verify `wire_sha256`, then continue `collection_next_offset`. This reads the same retained page, without recapture or loss of remaining patterns. Read observed counts, missing visit/time/URL coverage, `path_truncated`, omitted same-time events, timezone and goal meaning with the paths. Event order within a second and ambiguous DST wall times remain unknown. A fixed prefix limit is explicit; it never becomes a complete path. Arbitrary URL segments, all queries/fragments, visitor/client IDs and source row timestamps stay private. Safe static route categories and scoped opaque page keys distinguish observed pages without exposing private URLs; query-only page differences are deliberately collapsed.

`last_observed_event` can identify a place to investigate, but does not prove abandonment, a closed session, a failed form or its cause. Full-session/provider processing coverage, cross-device/person identity, campaign attribution and business meaning of a technical goal remain unproved. Read the existing goal catalog/discovery for its definition before treating an event as a submitted or qualified lead. Missing native IDs/times, pre-support windows and Jan 1 (possible prior-year visit IDs) return limited/unavailable paths without guessed joins; independent event counts remain available. These hit paths do not feed the visit→CRM linkage reader. Archive, revoked authority, transfer fence and offline restore stop autonomous continuation; they do not erase already retained public summaries.

The [published creation API](https://yandex.ru/dev/metrika/en/logs/openapi/createLogRequest) supports `hits` and `visits`, with no provider-side filter. Goal selection is therefore an owner projection over the bounded counter export, not a claim that Yandex exported only converting sessions. Provider limits include no current-day export, at most one year, a 3000-character fields list and a shared 10 GB prepared-log quota; the platform applies its existing stricter 16-part, 8 MiB/part, 32 MiB total and 100,000-row caps. This path never cleans provider logs.

For an exact visit → CRM inquiry → payment question, `include_linkage_identifiers=true` adds fixed `ym:s:clientID` and `ym:s:purchaseID` fields to that specific acquisition. They remain private in the retained originals. Pass the resulting summary `id` as `metrika_log_publication_id` to `get_sales_funnel` alongside the selected saved CRM publication; the existing owners verify and join their retained evidence without another provider read. ClientId is browser-cookie linkage, not cross-device identity. PurchaseId requires the same explicitly mapped CRM transaction definition. Multiple candidates remain ambiguous; missing linkage does not erase independent visits or CRM-marked money. Lag uses native visit time and CRM record creation/full CRM-marked payment, not a guessed form-submission time. The linkage flag is part of the same frozen command identity and unknown-create recovery rules.

Keep Logs visit-date and goal-occurrence-date calendars separate: occurrence totals cover only the exported visit cohort. Preserve provider cutoff/late-data unknowns; reconcile with an exact compatible aggregate report before claiming equality. Historical deleted-goal arrays do not establish that absent events were reliably observed. For robot results, read `robot_classified_visits`, `robot_unknown_visits` and `robot_share` together: the share uses classified visits, not the unknown remainder. Missing or invalid classification leaves the independent visits/goals useful. Non-robot visits do not establish commercial intent or identify employees/QA; these exclusions remain unproved. Logs exports are neither Webvisor replays nor click/scroll maps; use [available authorized host evidence](behavior-diagnostics.md) for those questions or a rendered form check.

`capture_metrika_counter_metrics` exposes the existing bounded whole-counter publisher for up to 31 Moscow days through the selected standalone connection. Use a stable `command_key`, the exact matching period, and no goal for a visits-only reconciliation. `get_metrika_counter_metrics` reads that immutable observation without another request. Only complete, unsampled observations with compatible counter/timezone/population support a numerical comparison; preserve the provider-response fingerprint and as-of. Missing or rejected exact goal evidence stays unknown. These whole-counter counts do not establish campaign attribution or paid outcomes.
