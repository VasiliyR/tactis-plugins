# Recurring client assignments through an external host

Read [the implemented platform route](platform-workflow.md#8-finite-monitoring-and-explicit-one-shot-pause) for the corresponding exact tools and retained artifact/effect boundaries.

Use for substantial-change control, a requested weekly material, ongoing assigned optimization, or return to a saved decision for one project/account. Deliver the useful result now when possible, retain it, and manage the supported native instruction through its lifecycle. Reuse the current tools, [foundation reads](foundation-reads.md) and [durable continuation](durable-continuation.md); host authored reviews and finite server monitoring are separate mechanisms; the server monitoring/action route below supplies bounded checks and explicitly armed exact pauses, without granting general advertising authority. The external agent interprets facts. Independent Tactis workers collect data and numerical observations; they do not start a model turn.

A native recurrence, Tactis delivery policy, lease, task and saved Work are separate objects. Quiet/empty polling needs no invented result or acknowledgement.

## Choose the assignment and its result

Reuse the known client context and exact relevant Work. Choose the useful result from the request or the working goal and observed data; the user may change the choice.

Prepare the first useful result and select the next check from the decision window, known calendar and source maturity. When the current assignment and host allow recurring work, create or update one actual host instruction with that Work locator; do not require a separate scheduling request or a timing questionnaire within already granted authority. Explain the chosen cadence and let the user change it. Ask only when a material choice cannot be inferred or the host requires authorization. Without a scheduler, retain the exact next check for the next turn and say that it has no active schedule.

| Request | Useful result in the user's chat | Message rule |
| --- | --- | --- |
| «Проверяй расход и сообщай о существенном изменении» | Change card: compatible before/after, affected scope, first useful investigation, limitation and next check | Exception-only: new material change, new blocker or recovery; unchanged checks use a verified quiet outcome |
| «Каждый понедельник готовь итоги и следующий шаг» | Weekly note: comparable indicators, changes, unresolved work, up to three grounded priorities and one concrete next step | The requested material is produced at its agreed cadence even without a new alert; do not invent an incident to justify it |
| «Вернись к этому решению после зрелого окна» | Decision review: original intent, actual application state, available observation, remaining uncertainty and next decision/check | At the agreed revisit condition; waiting and the next useful check are valid results, not a successful effect |

Daily authored control uses actually available completed days and the selected comparison rule. A finite server rule with a separately authorized one-shot exact pause is available through the platform route; neither is a guaranteed real-time spend ceiling. A weekly note may include a due decision review in the same instruction. Reuse the relevant instruction instead of multiplying schedules for each product involved.

## Use the available host scheduler

Use the host's exposed scheduling tool and its complete creation/update receipt. Include the exact project, account and selected Work, so the next turn resumes the original decision. Do not add a package audit, synthetic Work probe or repeat status read before every schedule. Handle an actual compatibility/access rejection through the existing recovery path. A missing tool or failed creation leaves no active schedule.

State the verified execution mode and its limitations. Local scheduled work requires the computer and application to remain available. A closed or sleeping host is not an active agent. Cloud access and ZCode scheduling need their own proof; do not infer them from remote MCP availability. If no supported scheduled turn is available, perform the available manual result and save its next check, explicitly without an active recurring control.

Keep states separate: source availability/coverage; native instruction ID/status/time; last actual turn; saved Work/committed receipt; observed message visibility. A created recurrence is not a completed run. A technical Work probe proves its observed mechanism, not installed acceptance of this procedure, quiet repeats or a useful weekly result.

## Set one bounded instruction

Use the known project/account, timezone, event definition and decision window. Select the cadence, comparison and next check from observed lag, business calendar and the working goal. Retain a known deadline; a missing end date alone does not require a question for a host instruction that the user can pause. Preserve selected goals; an unconfirmed technical event is not a qualified lead or sale. Saving authorized analysis needs no renewed consent.

Use the host's native recurring instruction in the existing chat when supported. Show where the user can view the runs, pause the instruction or change its time. Do not create a second Tactis recurrence or enable delivery policy just to schedule this weekly check. A reporting or monitoring assignment stays within reads and ordinary Work. If the current assignment also authorizes supported campaign optimization, carry its selected scope and existing limits into the same instruction and use the normal [current actions](current-actions.md) path when the evidence justifies a change. Scheduling adds no campaign, provider or spending authority; current owner checks and the original finite money boundaries still apply. An unsupported resume or a new spending phase is not made executable by a scheduled turn.

Prepare one instruction in the user's language: exact project/account and Work; useful material; metric/goal when relevant; timezone/cadence; any known deadline; comparison window and lag; material-change rule or revisit condition. Keep notification preferences in the host's supported setting. Use the complete returned ID/status/time/target; read status only if the receipt lacks a needed fact. A created instruction has not yet completed a run. Recover a lost creation response before creating another schedule.

Example user instruction (illustrative thresholds, not recommended defaults):

> До 30 ноября каждый понедельник в 10:00 по Москве проверяй проект «Клиент А», выбранный кабинет и цель. Сравни сопоставимые завершённые окна с учётом задержки конверсий. Сообщай, если CPA вырос одновременно на 25% и на 500 рублей при минимум 20 событиях в каждом окне, либо возник новый блокер контроля. Сохраняй результат и следующий check в Work. О прежнем неизменном состоянии повторно не уведомляй. Рекламу и настройки не меняй.

Keep the resolved project/account IDs and instructions in the host prompt. Record the agreed scope, threshold, end date and next check in the existing Work/continuation fields; do not invent an automation payload field or promote the instruction to confirmed business memory.

For a weekly material, an illustrative instruction is: «До конца ноября каждый понедельник в 10:00 по Москве готовь по выбранному клиенту итоги зрелых окон, статус прежней проверки и один следующий шаг. Сохраняй полный короткий материал и возвращайся к выбранному решению по его реальному условию. Рекламу не меняй». The month/time are illustrative, not defaults; use the user's actual scope and dates.

The end-date check in the prompt stops useful work before Tactis reads/writes; it does **not** cancel the host's recurrence. Configure a native end date or actually pause the schedule to stop future turns. Where only manual pause is supported, explain that explicitly. Never promise automatic cancellation based only on a date in text.

## Run and save the useful check

1. Check the instruction's end date first. Read `get_project_brief` and `get_work_session(current_continuation=true)` for the full supported current continuation of the exact account; follow the existing resume procedure. A grant expiry, denied scope or source failure is a blocker, not unchanged performance.
2. Read ready immutable evidence for the requested windows; use existing `capture_analysis` only if needed and supported. Compare compatible sources, goal definitions, attribution, units, timezone and mature periods. Missing dates, partial coverage, immature data or an insufficient denominator make the relevant comparison unavailable. Do not fill zeros, extrapolate a partial account or infer causal uplift.
3. Compare with the prior saved control and unresolved issue. Describe the observed change, plausible interpretation, remaining unknowns and next useful step. New calendar dates alone do not make the same unresolved blocker a new alert. Recovery from a known blocker can be useful new information.
4. Reuse the observed schedule/run identity when the host supplies it; never invent an occurrence from a date. Restore the existing Work and pending Plan/Application before repeating an action. An unknown result follows that original command key/payload and owner recovery, not a new write. A missing native run ID limits claims about host occurrence deduplication; it does not prevent ordinary authorized work through the existing command and continuation identities. A later run does not make an unchanged unresolved incident new.
5. Produce the selected material when due or when a useful new result exists. An unchanged quiet check needs no extra Work solely to prove it ran. Save the useful compact result through `record_work_session`: `weekly_review` for the weekly note; supported `assessment`/`no_action` for a bounded control, or `experiment_review` for an interpreted existing measurement. A selected optimization uses the existing exact plan/Application/readback, and the saved result states what actually changed. Before sending, apply [the shared field-budget check](save-recovery.md#fit-a-rejected-or-oversized-command); a complete larger material keeps its supported exact-readable body/reference instead of being copied into `summary`. Use supported exact references, limitations and next check, retain the committed saved receipt for that material. Follow the existing command replay and continuation CAS procedure, preserving other active decisions. Ordinary Work is valid without a head or A1; do not invent versions or an assessment to save a limited result. Keep scope, the current issue/change rule and the last signal described in the appropriate bounded Work fields; no separate alert store is required.

No analysis is fresh merely because its narrative was carried forward. An unavailable save means the result is not saved; say so and do not acknowledge successful completion.

## Produce the concrete material

### Substantial-change card

Show the metric's actual scope, windows, units and comparison status before interpreting its change. A breached agreed threshold is a reason to investigate, not proof of waste or causation. Use account comparison guards; do not bypass an incompatible source/scope/calendar/money proof with manual subtraction. For CPA, require compatible goal meaning, mature events and sufficient denominators; never sum campaign CPAs.

When the complete same inventory contains up to ten campaigns and both cost publications are usable, read their existing campaign economics/coverage, explicitly compute before/after spend deltas, rank up to three largest positive RUB changes and reconcile account delta with the signed remainder. If no positive movers exist, say that. This is a bounded external calculation, not a new owner delta API. For a larger/partial cabinet, give the available account result and a targeted investigation, without claiming a global campaign top from a sample. Missing baseline is unavailable comparison, not zero spend.

**Illustration only:** compatible totals 100,000→130,000 RUB (+30%); A +20,000, B +8,000, C +2,000, other campaigns 0. With an agreed 25% threshold the useful card shows those addresses and proposes first reading A's compatible clicks/CPC, if available. It does not assert why spend rose or whether more spend was profitable. With offsetting negative deltas the remainder may be negative; preserve it and reconcile sums.

Finish with one executable next read/question in the existing Ads path and the saved Work locator. Do not promise an advertising change or ask for an already supplied threshold again.

### Weekly material

Produce the actual short note, not a promise to prepare one later:

1. Actual client/account, completed windows/lag and available indicators with units/coverage.
2. What changed on compatible evidence; stable evidence stays stable. Separate observation, interpretation and unknown business meaning.
3. Status of the prior selected work: prepared, reported applied, provider-confirmed, waiting or observed, as established by its exact sources.
4. Up to three grounded priorities within known constraints; fewer are preferable to invented work. Specify an object/material, responsible actor and dependency; attributed effort/budget is not confirmed memory or spending authority.
5. One concrete next step and actual/proposed check condition, labelled accordingly; exact saved Work locator from its committed receipt, with required material-owner readback.

Reuse the substantial-change card when relevant. If sales or goal meaning is missing, a useful traffic/spend finding and the one necessary business question suffice; do not call technical events sales. With no material change, prepare the requested stable-week note and status of unresolved work. This is a regular requested material, not a new exception alert. Reports HTML/PDF is optional only on request; no automatic client publication or messaging.

### Return to a saved decision

Read the exact original Work/card and its user-selected condition, not merely the latest unrelated Work. Reuse [Experiments](experiments-workflow.md#return-to-facts-not-the-draft-calendar) for exact plan/Application/measurement/outcome linkage, real maturity and sufficiency. A hypothetical date in a preparatory card does not move frozen windows. An existing saved decision does not authorize execute, a new observation/capture outside scope, or creation of an effect solely to obtain a measurement.

Deliver: original question/selected material; state of actual application; available observation and its window; limitations/confounders; a bounded decision to retain, investigate or wait; next check. A missing Application or measurement locator is an explicit unresolved dependency. A user's report of manual application remains attributed; it is not a provider receipt. Even a mature pre/post outcome is observational, not causal uplift. If the result is waiting/partial, save that useful limited review and its next condition without pretending the underlying programme/task is complete.

## X5: programme and selected check → Automation → Growth

Use when Growth or Experiments in this same chat has already supplied a programme/selected check. This is one external model using procedures, not a new engine or message to another agent.

**Receive and read:** exact project/account; actual saved programme Work ID and its local item label; selected material/decision/check Work ID; exact source/plan/Application/measurement locators where they really exist; user's choice, resource constraints, review condition and remaining unknowns. Read the necessary exact Work and owner evidence. A local item label identifies content inside that Work, not a new global ID or typed foundation reference. An absent locator is missing; retain attributed unsaved input as such and do not invent an ID. Reuse the already supplied brief, scope and choice; ask only the unknown that changes this review.

**Produce:** the weekly note or decision review above, mapped to that exact selected item. State what was prepared/applied/observed and what still waits, whether the original condition can now be assessed, what resource/dependency changed, and the next useful step. Preserve the selected material and constraints within existing bounded Work fields. Shorten surrounding prose rather than silently dropping its criterion or claiming that an unsaved material was retained.

**Return to Growth:** after the committed Work receipt, carry the programme locator/item label, review Work locator, actual observations/limitations and the recommended next resource/priority decision. Continue with [Growth](growth-workflow.md) in the same chat if requested: revise the specific item against current constraints, not the entire programme by default. Reports can render a requested result; it is not automatically sent. Neither a weekly note nor an unchanged observation means the programme achieved business growth.

**Missing/return:** without the selected check's evidence, produce the known programme-item status, the exact missing locator/date/denominator and one useful next check. On return read the saved programme and review plus relevant current owner evidence. Do not repeat the brief or fabricate effect/maturity. Save an intermediate task-linked result with `task_resolution="keep_pending"`, leaving its task open and without delivery acknowledgement. Complete the task only with its actual requested result and committed saved Work receipt.

## Notify and return without noise

For exception-only control, reuse the prior saved result and next check when nothing changed; a quiet repeat needs no new Work solely to prove it ran. Use the host's supported quiet outcome for unchanged state or the same unresolved blocker. A new material event, new blocker or recovery gets one short useful message: what changed, the exact scope/window, the important unknown, next action and saved Work reference. Avoid routine “everything is fine” alerts. For a weekly material, deliver the requested note at cadence even if there is no exception. Do not suppress that material merely because one issue is unchanged.

If the user defers a specific unresolved question until an aware date, preserve its exact Work/question and the agreed early-return exception. On a check, evaluate a new material exception first, then the deferral, then the due revisit. Do not defer all other work or a new blocker by accident. Record the agreed date/exception in existing authored fields; continuation `revisit_at` is not itself a native timer. Do not claim verified silence from a written deferral alone.

Confirm the actual host notification behavior before promising silence. Writing “stay quiet” in the prompt is not proof that the host suppresses completion notifications. If every empty successful run necessarily alerts the user, disclose that gap and do not claim the requested quiet control is accepted. A saved Work is not a human delivery/read receipt; record a signal's content without inventing proof that the user saw it. Cross-system notification exactly-once is not guaranteed by Work replay.

When the host becomes available after a gap, inspect the last real check and current facts; give one current useful result rather than a burst of obsolete missed alerts. Never invent checks while the host was unavailable.

The user can open the host result and ask “Разбери причину” or “Продолжай контроль”. Read its exact Work and current relevant evidence. Another authorized host can resume those conclusions from Tactis, but the original schedule does not transfer automatically. Any later advertising action follows the existing exact plan and chat-choice procedure.

## Change, pause and stop the native instruction

Recover the exact native ID from its saved setup and inspect current state. For an authorized change of time/frequency/material, update that existing instruction with the supported current schema, preserve other settings, and read back target/time/status before claiming the change. Do not create a duplicate just because another host can read the same Work.

For pause/stop or the end date, apply the host's actual supported pause/delete/end mechanism and inspect the result. A `deleted` or confirmed already-absent result differs from an unconfirmed timeout. If native management is unavailable, state that stopping is pending and show the exact manual pause location; do not claim a prompt date removed the recurrence. Once the prompt deadline passed, stop useful Tactis reads/writes first even if native cleanup is still pending. Saved Work remains historical, subject to its own permissions; pausing a control does not pause campaigns, revoke access or close programme tasks.

Existing proactive delivery is separate from a native recurrence. Follow [the exact policy/claim/result/ack recipe](proactive-delivery.md) for an existing due task under its permitted host-bound policy. Finish the task's result and retain its committed saved Work receipt before acking its actual current lease; intermediate Work stays `keep_pending` and is not acknowledged complete. Server `delivered` is agent acknowledgement, not a human notification read receipt. Do not modify policy/grants or create a second task/schedule to work around a missing host gate.
