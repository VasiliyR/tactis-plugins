# Sales: обращения до оплаченной продажи

Read [the implemented platform route](platform-workflow.md#7-crm-calltracking-and-offline-conversions) for the corresponding exact tools and retained artifact/effect boundaries.

Use this procedure for the linked Sales cycle: inquiry quality, processing gaps, one useful assignment, its execution report, paid outcomes and return. Start with “Где обращения теряются до продажи и что сделать первым?” or resume the client's existing check. The connected source reads paginated deal/payment observations and current stages when its actual tools are installed; complete stage history and unsupported quality definitions remain assisted/unknown. A private inquiry CSV supports elapsed response SLA through the separate route below. Human-confirmed CRM aggregates remain a supported partial source. Author interpretations externally; current status/payment observations do not prove causes.

## Read the minimum useful evidence

For a question connecting CRM outcomes to advertising/site facts, use [the marketing data matrix](marketing-data-matrix.md). It preserves exact CRM source/cohort definitions and separates source summaries from proven campaign observations. Inspect blocked joins and unavailable cells before claiming campaign lead quality or a paid-sale cost. Keep the original source reader below for its own evidence and follow-up.

### Toolbox by stage

| Stage | Actual tools and useful result |
| --- | --- |

| Read actual automatic CRM | `get_crm_source_status` → `capture_crm_source` only if needed → `get_crm_source_job` → exact `get_crm_source_publication`; async admission is not a fresh completed source |

| Deliver and continue | Known quality/current-stage/CRM-paid groups → one ready assignment; `record_work_session` → committed saved receipt, then the relevant changed source on return |

[Invariants](invariants.md) owns shared access/save/replay rules; the CRM mapping/coverage and payment distinctions below are specific. Keep **qualification · current open/closed stage · processing speed · CRM-marked paid · bank/refund outcome** separate. A source exposing one does not fill the others. For “где теряем” without history/SLA, deliver the supported groups and exact missing-stage/time check, not a loss-cause verdict.

### First human response from a private supplied cohort

When the catalog exposes `save_response_sla`, select an existing private UTF-8 CSV material; the owner verifies its exact bytes and SHA256. Use real stable inquiry IDs, timezone-aware creation and first-human-response timestamps, a blank response for unanswered inquiries, an explicit creation period/timezone, source `observation_through` and definition/completeness. Reuse a chosen SLA in seconds when available; its absence does not block measuring known response durations, answered-only P50/P95 or unanswered counts. Recommend a threshold only when the decision needs one, from the observed base and business handling limits; ask for its concrete choice rather than inventing zero. Do not infer a human reply from assignment, CRM modification or an automated message. A missing actual timestamp source remains a prerequisite. Capture/download time does not replace the source cutoff.

This project-only route requires no CRM, OAuth or advertiser. It retains aggregate counts and answered-only P50/P95; SLA classification/ratios and overdue/pending judgments remain unknown when no threshold is selected. Unanswered inquiries are right-censored; do not replace their delay with zero or call answered-only quantiles the full cohort distribution. Elapsed time is not business-hours time. The supplied definition/coverage and cohort do not prove provider or advertising attribution. Use the full successful save receipt and retain its exact `marketing_publication` reference in Work. On later recovery or an unknown/incomplete save response, read `get_marketing_publication` with that publication ID and preserve `kind=response_sla`; raw IDs and contact rows remain private.

### Connected automatic CRM source

When the actual installed catalog exposes `get_crm_source_status`, `capture_crm_source`, `get_crm_source_job` and `get_crm_source_publication`, read current account/connection status first. Human setup is in the cabinet: webhook input, one CRM funnel, company/contact buyer meaning and explicit CRM payment meaning. Never ask the person to paste a webhook URL into chat or forward credentials to a tool. Human connect/revoke have no MCP tools; an unconnected/denied source remains a concrete setup prerequisite.

Use the actual source capture tool with a new command key, exact active connection/generation and chosen scope. Admission returns a durable job immediately; wait/read that job through the actual catalog. A waiting/running job is not a fresh publication. Repeat the same command/input to recover its receipt, without a new consent question; stale generation requires current status. On completion read the exact publication and retain its id/digest, mapping, scope, capture interval and separate deal/payment/buyer coverage. Failed acquisition never means zero deals; a partial publication reports observed groups and missing coverage. The old `get_crm_publications` human-import list is a different source and cannot resolve this locator.

Sales can choose a creation window for a selected-deal question or all_visible_category to inspect available current deal context. Lifecycle uses all_visible_category because old deals can receive new payments. Capture follows deal pages up to 5000 deals and payment pages up to 100 per deal, with a durable job budget; inspect actual coverage, provider total and reasons instead of assuming the visible category is complete. The linked-lead counts cover LEAD_ID references in these deals; unconverted leads outside the selected deals are not covered. Duplicate order pages fail acquisition; a payment linked to multiple orders leaves their paid proof unknown.

For a question about the whole inquiry funnel, use `capture_crm_source(include_leads=true)` and read its job and exact publication. This also reads the bounded lead history, including inquiries with no selected order. Read `sales.lead_status_catalog`, discuss qualification using its human names and reuse the confirmed definition through `lead_qualified_status_ids` / `lead_qualification_definition`. These are current statuses, not the history of everyone who ever qualified. When Calltouch is part of this business, use the already configured `calltouch_site_id` and exact CRM fields `calltouch_call_field` / `calltouch_form_field`; only the administrator supplies missing field mappings through the existing setup process. A UTM label, phone similarity or visitor ID alone is not an exact call/form-to-order link.

Call `get_sales_funnel` with the exact CRM publication, optional saved Calltouch publication and inquiry-creation period/timezone. Read counts, coverage and linkage together: unconverted inquiries remain in the denominator; one inquiry with several calls/orders is not several people. Show current qualification, linked orders, full-paid orders and unknown payment proof separately. Report matched, unlinked, ambiguous and outside-cohort calls/forms and the reconstructed source-to-order share. Partial history gives a partial result. Source buckets describe the recorded source, not verified campaign attribution. Save the returned `foundation_refs` / `platform_refs` and the useful next step in Work; retain the committed receipt. A fresh chat reads those exact sources rather than silently replacing the cohort.

Current P/S/F stages mean open/successful/unsuccessful. A first capture exposes this funnel's `sales.stage_catalog` with provider names and stable IDs, plus named `current_stage_counts` and `lost_stages`. Discuss qualification in those human-readable names and reuse an already confirmed meaning; do not ask the person to supply technical stage codes. Then `capture_crm_source` accepts the corresponding exact `qualified_stage_ids` and `qualification_definition`; the server validates the IDs against the current catalog. A missing/ambiguous name remains a specific definition gap. `qualified_unit=current_stage_deals` and bucket `qualified_current_stage_deals` count deals in those current stages; `lead_linked_deals` counts deals carrying a lead link, while coverage `linked_lead_count` counts distinct observed lead references. None is a unique-person count or a proved CPL denominator. The publication reports current matching stages, not everybody who ever qualified. MOVED_TIME is the time of entry into the current stage; DATE_MODIFY is not a qualification date. Missing stage time remains unknown. A named unsuccessful stage is its configured label, not an invented private loss reason or response SLA. Source/UTM buckets include unlinked observations explicitly; UTM labels alone do not prove a canonical campaign match or causation.

For calendar payment questions, select the exact all-visible CRM publication in the marketing data matrix. Read `fully_paid_orders_period` by the first fully-paid threshold date separately from `gross_paid_amount_<currency>` by payment occurrence date. An instalment can contribute money without completing an order, and an old deal can receive a payment in the current period. Preserve currency, calendar, receipt as-of and coverage; incomplete or unproven evidence remains unavailable. CRM-marked payment does not prove bank settlement, refunds, net revenue or an advertising campaign connection.

The accepted payment rule is full CRM-marked paid amount in the deal currency reaching its positive agreed deal amount, with required dates and complete payment pages. A successful stage does not prove payment; a deposit does not prove a fully paid purchase. Missing payment fields/date/currency/coverage remain unknown. CRM markings do not prove bank settlement, refunds, shipment, profit or causation. Cohort exactness requires the private Lifecycle server port and its completeness/rule/namespace gates; do not obtain buyer/order keys in chat or infer first-ever buyers from a short observed history. Channel/consent/suppression remain separate prerequisites.

Save this bounded Sales result and one ready assignment with its publication locator and limitations. If the actual current Work schema exposes `PublicationEvidence.kind='crm_source'`, use that exact kind, publication id/account and fingerprint=public digest in its supported evidence field, retain its committed saved receipt. An ordinary CRM Work needs no invented Analysis publication or typed assessment. If the actual catalog/schema lacks that kind, save ordinary attributed/assisted Work without inventing typed evidence. On return read the saved locator through `get_crm_source_publication` and current active compatible connection, then capture updated observations if needed. Same-binding credential rotation may preserve identity; revoke or portal/category/buyer/rule drift denies old source reads. Record differences as observations, never a causal effect of the assignment. Automatic source reads do not run external Sales reasoning while the host is closed. If shared source tools are not yet installed, use the assisted path below without claiming automatic availability.

### Confirmed CRM events into Metrika

Use the existing `prepare_offline_conversions` path with `source_crm_publication_id`, one `event_kind` (`qualified_lead` or `paid`) and the explicit `period_start`/`period_end` in the configured counter timezone. This selects up to 500 eligible events within at most 31 calendar days. It prepares an exact command, without uploading or exposing visitor IDs. Paid events require full CRM payment proof and use confirmed payments through the purchase timestamp, in the configured currency; amounts are decimal currency units, not integer kopeks. Partial payments still matter for financial analysis but are not exported as fully paid purchases.

The source capture must already carry the actual `offline_identifier_field` and `offline_identifier_type`. Ask the CRM administrator for the exact single-valued string field code which actually stores ClientId, UserId, Yclid or PurchaseId; they can inspect Bitrix24 deal/custom-field settings or its `crm.deal.fields` response. A field title, phone, email, native deal ID or buyer HMAC is not a substitute. The capture checks field metadata and keeps values private. Without this mapping, use the concrete setup prerequisite; do not ask for personal rows in chat. For qualification also require the explicit stage mapping and a known current-stage entry time. Won stage alone never supplies paid meaning.

Read the returned `crm_preview`: exact publication/digest, counter, goal, meaning, currency, selected/excluded counts, coverage and age warning. Common `offline_preview` gives actual event dates, counter/timezone/currency, targets and refresh window for all supported intakes, including private CSV; its material locator/hash identifies that frozen file. Explain exclusions and obtain the applicable permission for this exact external transfer. Then `upload_offline_conversions(command_id,digest)` → `check_offline_conversions` / `get_source_command`. Recover the original command after a lost result; do not create a new command to bypass event deduplication. Credentials and source authority are rechecked before upload.

`processed` is file processing, not matched visits or improved advertising. The 21-day rule concerns the time from a visit to file processing; an old event warning is not a claim that the API rejects the file. After processing, read `get_source_command` and its current `refresh_plan`. Select the actual advertising source with the same counter and reporting calendar. Use only `closed_refresh_start` / `closed_refresh_end` in `capture_daygrain`; the frozen requested window can still include today and is not itself an admissible closed-day range. Read the resulting job/publication and fresh goal receipts before reassessing the channel/goal. If `pending_start` / `pending_end` remain, save those dates and `next_check_at` in Work, then reread the same command after the day closes; do not re-upload the events. A history gap remains explicit. Never assign the CRM counter to an unrelated source or call cached metrics refreshed. Missing matching source, calendar or processing leaves a concrete pending follow-up.

Resolve the authorized project/account and resume relevant Work using [durable continuation](durable-continuation.md). Reuse known business definitions; do not start with a long technical brief. Read `get_crm_publications(project_id)` for human-confirmed CRM facts. The tool returns a bounded project list, not individual deals: select the exact account, source and period, and the latest replacing version for that source/period. Preserve its id, version, digest, mapping, confirmation time and exclusions. Do not sum corrections or overlapping origins. If the needed record is outside the returned list, its absence is not proof that no import exists.

Read the meaning of the mapped date and qualification/sale statuses. A date column may represent creation or another event; confirmation time is not necessarily the status cutoff. If materially unknown, ask one short question, for example: “В этой выгрузке дата — день обращения, а «продажа» означает оплату? На какую дату актуальны статусы?” Record the answer as attributed user information, not automatically confirmed business memory. One accepted row must represent one inquiry, not a stage event or repeated purchase. A completed calendar period does not establish a mature sales cohort or complete coverage.

For this account-level task, advertising attribution is optional. Use [foundation reads](foundation-reads.md) only when a material advertising question calls for them; do not collect the entire account or manufacture A1 merely to save a Sales result. Metrika goal events are not CRM inquiries, qualified leads or payments without a proved definition and linkage. CSV upload/mapping/confirmation is a separate human flow described in [the CRM procedure](mvp-workflow.md#scoped-facts-and-crm), not an agent upload or CRM edit.

## Give the result and one ready assignment

Present known totals with source, period, status cutoff when known and accepted-row coverage. For a human-import mapping where `qualified` includes `sales`, display sales and `qualified - sales` as separate groups; never add sales to qualified again. For a connected current-stage qualification mapping, current qualified stages and independently paid orders can overlap or be disjoint; do not subtract them without proven membership. Keep rejected and unknown separate. These are status groups, not sequential funnel stages. Unknown is not rejected, and inquiry without a sale status is not a demonstrated lost sale. Classification gaps leave known qualified/sales counts as lower bounds; ratios must retain that limitation. Zero denominators give an unknown ratio. Preserve invalid, duplicate and out-of-period exclusions. Unlinked rows cannot be assigned to campaigns; do not use account counts as campaign proof.

Choose one check that can resolve the most material observed gap. Prioritize unknown statuses when they prevent interpreting the sales result; otherwise inspect qualified inquiries without a sale status, while preserving the possibility that they remain open. Do not claim that the chosen check is a proved cause or a quantified revenue loss.

**Conditional illustration, not client evidence:** a repair business has 100 accepted September inquiries, with statuses as of 9 October: qualified 50 (including 20 paid sales), rejected 30, unknown 20. A useful answer is:

> По этой выгрузке 20 обращений имеют статус оплаченной продажи, ещё 30 — квалифицированы без статуса продажи. 30 отклонены, у 20 статус неизвестен. Это итог по принятым строкам сентября, а не доказанная потеря 80 продаж: часть обращений может оставаться в работе. Где именно они останавливаются и сколько ждут ответа, выгрузка не показывает.
>
> Первым шагом предлагаю проверить 20 неизвестных статусов: сейчас они мешают понять результат обработки заявок.

Provide the actual assignment immediately, with details drawn from the selected evidence:

> **Задание владельцу продаж:** в своей CRM проверь 20 обращений сентября с неизвестным статусом в выбранной выгрузке. Раздели их на открытые, закрытые без продажи и оплаченные; для закрытых укажи имеющуюся причину, для открытых — следующий шаг и дату проверки, если они заведены. Не придумывай причину при её отсутствии. Верни обезличенные итоги: сколько проверено, сколько в каждой группе и сколько статусов остаётся неизвестными. Итог готов, когда все 20 учтены в этих группах и указан день среза. Срок — предлагаю до следующего разбора; конкретную дату выберем с тобой.

This proposed role and timing are not a recorded assignment to a named manager or a promised deadline. Use an already agreed date when available. Adapt the count, cohort and check to actual evidence; omit the illustration's numbers for real clients. If the user supplied a completed check, incorporate its attributed findings and identify the remaining check rather than requesting it again. Do not send the assignment, change CRM, contact clients or claim a manager has received it. The useful material is the ready text saved in Work.

## Assisted product cycle: quality, processing, execution and payment

Reuse the selected client, confirmed definitions and existing assignment. In one turn, show what can be distinguished: qualification, open processing, closed result and payment. A qualification status does not determine open/closed; a CRM successful stage does not prove payment. Treat additional stage counts or completion reports from the business as attributed evidence, not a confirmed import or typed publication. If the source lacks these distinctions, give the supported quality result and one targeted check rather than filling missing families.

For current stages, accept a small already available CRM summary with source/filter/cutoff and actual stage meanings; do not require the specialist to assemble a complex cohort. A snapshot can show where open deals currently sit. It cannot show reached-stage conversion, time in stage, skipped stages, returns or where closed deals were last open. Use age/first-response thresholds only with the corresponding timestamps and a business definition; creation age is not stage age, and last modification is not first human response. If unavailable, choose a quality/open-status check with an explicit unknown instead of an SLA verdict.

**Conditional linked case:** a confirmed inquiry publication shows 100 accepted, qualified 50 including 20 sales, rejected 30, unknown 20. The business confirms the sale mapping means paid and separately reports 30 open inquiries at “Предложение” on the same cutoff. Give the known status groups and this attributed open count without summing the two axes. The first useful check may still be the 20 unknown classifications; if already resolved, use the existing processing question and prepare a check of the open proposal group. Do not call 30 open inquiries lost or overdue without more evidence.

After the chosen assignment, record whether it is prepared, reported performed, or still awaiting a usable result. A report “проверили” without counts/source/cutoff can establish an attributed completion claim, but not payment or coverage. Read the next confirmed publication when available, retain its source and definitions, and show new paid counts only when paid meaning is confirmed. Same period alone does not prove identical cohort membership; changed coverage, corrections or definitions prevent a clean comparison. Do not claim that new payments came from the checked group or that the assignment caused them without matched evidence and an appropriate effect check.

Weekly return: review the outstanding assignment and changed CRM evidence; monthly return: review comparable completed cohorts and the next processing priority. Daily checks need an actually fresh connected-source publication or new import. Without either, continue the saved assignment or obtain its result; do not announce a fresh daily Sales signal. A supported Automation/host turn is a separate prerequisite for scheduled reasoning. Ordinary Work supports this cycle without a new CRM, task engine or message channel.

## When data is missing

If there is no usable publication, give the available finding and a specific first assignment instead of an empty funnel or generic advice. For example:

> Пока нет подтверждённых CRM итогов: по событиям сайта нельзя сказать, сколько обращений дошло до оплаты. Первое задание владельцу продаж — подготовить обезличенные итоги одной когорты обращений: период их создания, дату среза, число обращений, открытых, закрытых без оплаты, оплаченных и неразобранных; пояснить статусы и исключения. Это позволит отделить ожидание от закрытых обращений и выбрать следующую проверку. Готовность — все обращения учтены без пересечений, определения и дата среза указаны; персональные строки сюда не нужны.

Ask only for the material missing definition or this bounded aggregate. User-provided totals remain attributed information, not a human-confirmed CRM publication. If an import exists but is partial, show its useful known groups and request only the missing coverage/meaning. For “на какой стадии/сколько дней” explain the additional minimum: defined stages, same-cohort counts reaching each stage, open remainder/closed reasons, status cutoff and first-response/transition-time distributions from the business's own CRM. Current CSV does not retain these fields; preparation of those aggregates is a task, not an implemented stage reader. Do not request personal records or label missing durations as zero.

Ask for the assignment's result only if it is still missing. Distinguish an attributed completion report, a newly confirmed aggregate and remaining unknowns; save the useful update and one next step.
