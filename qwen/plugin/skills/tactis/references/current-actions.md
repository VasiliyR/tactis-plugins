# Current account and action paths

Use the actual current tools and operation schema. Native campaign, group, ad and keyword IDs are decimal strings on the MCP wire. Preserve every digit; never convert them to JavaScript numbers. Owner fingerprints and immutable receipts retain their original representation; do not recompute their identities from a reformatted display response.

For a connected diagnosis → selected improvement or SEARCH draft → status/result return, use [the Ads workflow](ads-workflow.md). It supports both independent entry branches and reuses the exact action/recovery procedures below.

## How is my advertising doing?

Use [session entry](session-entry.md) for the client and [addressed foundation reads](source-current-metrics.md) for an ordinary status question. A full inventory, landing inference or current Ads action is needed only when the user's task or a relevant evidence gap calls for it. Save a substantive result through [durable continuation](durable-continuation.md); ordinary Work remains supported even when the current-head feature is absent.

These sources assemble a schema-valid proposal; current state still decides admission. After freeze/read, preserve **chat-choice → exact execute → per-object readback** under [shared gates](invariants.md).

Read the exact existing group, keywords, negatives and relevant ads, completing every needed page. Pin fresh native scope and current object versions for the objects to be changed. A multi-title ad can be unsupported while a group-level negative change is supported; inspect per-object availability rather than treating every configuration family as writable. Do not flatten an unsupported ad to a single title or infer a writable version from a D1 fingerprint.

The catalog's `write_readiness` describes server/connection configuration, separately from object shape and the user's choice in chat. Its `legacy_connection_writes_enabled` flag concerns the old unscoped path; it is not the authority for a modern native-scoped operation. An operation-specific refusal remains binding even when `live_writes_enabled=true`.

Work access does not prove permission to freeze an Ads plan. For a refused proposal retain the useful draft and the returned reason: project/account access, scope, role or expired subscription may need the corresponding human setting. An unspecified `workspace_authorization_denied` leaves the particular cause unknown; do not widen permissions or bypass it through another path.

`get_operations_catalog` defaults to compact capabilities and readiness. The `propose_operations` declaration lists operation names and common fields compactly. When the selected operation's shape is unknown, pass its operation name and include_schema=true; other operations are excluded from that schema, while unsupported refinements and money/scope limits remain binding. Reuse an already known payload without another contract read. Do not request a whole catalog schema or infer that an advertised operation supports every provider object.

`get_operations_work` pages default to ten rows per collection; its maximum is 50, and requests above ten require one collection. Reuse the default for exact-plan recovery. A byte-limited page may include fewer rows than requested and reports page_limited_by with the actual next_offset. If an aggregate page gives zero rows for a collection, read that collection at its unchanged offset. Recovery task title/description are bounded and explicitly mark truncation; retain the task and parent plan/Application IDs even before Workspace delivery. These Ads pages are separate from Workspace `get_work_session` collections.

For modern operations, supply `analysis_basis` with the exact current analysis publication ID/fingerprint and native scope proof ID when required by the actual tool schema. Do not fabricate a data.1 snapshot or old binding as `facts_id`. Preserve unchanged keyword/negative sets under replacement semantics. Prepare a PAUSED ad variant where supported. Freeze the proposal with `propose_operations`; its full successful receipt already contains the immutable Plan ID, digest and before/after. Use `get_operations_plan` for later restoration or an unresolved/incomplete response with a known plan ID. Show the exact change, consequences and limits in chat. A returned `next_action` is navigation, not execution authority; a `preparation_only` plan remains non-executable. Reuse the user's existing authorization when it covers this action, objects and money bounds; ask and wait only for a missing or materially changed choice. Then use `execute_operations` with the saved plan ID and digest. Inspect Application and readback afterwards; never blindly retry an uncertain effect.

### Recover a lost execution response

Keep the original project, plan ID, digest and the Plan's original `proposal.command_key`. When all are known, call **`replay_operations(project_id, plan_id, command_key, digest)` first**: it returns an already saved Application and never dispatches a new effect. Its command_key is the original proposal's, not a new retry label, host run ID or guessed value. If it reports no existing execution or cannot be read, do not infer that nothing was accepted; continue the exact scoped lookup below and retain an unresolved state.

`execute_operations` can also recover its exact already admitted Application, but it is an execution entrypoint and must not be called as discovery when admission is unproved. Read/replay needs no new action consent; reuse the original exact choice. `queued` proves durable acceptance, while only `applied` with its per-object receipt/readback proves the provider effect. `unknown`, `partial` and `recovery_required` need reconciliation; none proves advertising benefit.

An explicit provider refusal is not a timeout. Preserve its code, safe message/details and Request ID, and report the actual Application state. If that state still requires recovery, use its existing recovery path; neither a readable refusal nor an empty inventory authorizes another dispatch. A generic permission code alone does not prove which role or connection setting caused it. Use the supported owner/admin correction for the stated prerequisite, without changing credentials or creating a replacement command key.

If the tool returns `operation_execution_outcome_unknown`, `ads_unavailable` or loses its response entirely, read `get_operations_work` with the exact project and plan_id and collection=applications, then read the returned ID with `get_operations_application`. Work returns paged summaries; follow the selected collection's next_offset when needed, and use existing plan/Application readers for full details. An unfiltered first page cannot prove no matching Application exists. Unrelated fact retry reads are optional and need their own bounded limit/offset; current native source jobs use list_daygrain_jobs/get_daygrain_job. If no matching Application is visible after the exact scoped read, the reader fails, or access is lost, report that verification is pending or forbidden; do not infer that nothing was accepted. Do not create a replacement plan, change command identity or blindly repeat execution. Reuse the user's existing choice for that exact plan; a recovered read requires no new consent.

For example, after consenting to one exact negative-keyword change the user sees a timeout: say “The execution response was lost; I will check the same plan.” A recovered `queued` means “Accepted, awaiting execution”; a proven `applied` means “The change is confirmed”; an unavailable read means “The state is still unknown.” Preserve the original references and next read in Work using [durable continuation](durable-continuation.md), retaining its committed saved receipt. On “What happened to that cleanup?” read those same references rather than propose the change again. A measurement still waiting for its frozen window is normal and does not block recovery acceptance; evaluate advertising outcomes later.

## Create a campaign from a domain

Fetch a bounded landing document and author a useful draft from its evidence. Choose the [working goal](session-entry.md#choose-a-working-goal) from the known purpose and useful facts. Missing geography may remain a clearly labelled assumption for draft copy; resolve it before an executable plan. Use [performance strategy selection](campaign-launch.md#choose-a-supported-performance-strategy) for conversion/value execution. Reuse known answers and accessible measurement discovery rather than adding a technical questionnaire.

Use the exact `final_url` exposed by the pinned landing manifest as copy.url. The current `creative_landing_changed` error identifies `reason=ad_destination_differs_from_retained_landing`, the URL field and safe expected final_url; it does not prove the page text changed. URI origin/default-port/root normalization is bounded; path, query and fragment retain their selected identity. Read the pinned manifest and correct the mismatched input only for the intended same destination. A different destination needs its own exact source and visible chosen material; a new capture is useful only when that evidence is needed.

In each creative's `evidence_ids`, use retained evidence object IDs accepted by the exact schema, such as the pinned `landing_source.artifact_id`; D7 span references belong only in `landing_source.evidence_refs`. Do not put span references or an Analysis publication ID into the legacy evidence-object list. A modern `analysis_basis` remains separate. For `evidence_not_found`, correct the source locator from the retained manifest; changing permissions or recapturing the same page cannot repair a wrong object ID.

Use `creator_account` native scope and a current compatible analysis basis. Create only the graph declared by the operation schema, in PAUSED state. If the creator schema cannot include negatives, make their separate exact group change visible after creation/readback; do not claim they were included. Read exact new IDs and graph state. Creation, moderation and finite paid launch each need an exact operation covered by the user's choice; one explicit instruction may already authorize all three within its bounds. Configuration readiness and a preview do not prove an applied effect; the user's choice does not prove provider readback.

Native SEARCH/NETWORK Creator accepts either the existing single `copy.title`/`copy.text` or complete `copy.titles` (1..7) and `copy.texts` (1..3), with the same exact URL and retained landing source. Author the useful alternatives from the offer; each combination keeps its source binding. Do not reduce the chosen alternatives to a first title/text. Optional `ads[].images` selects up to five existing image Materials as `{material_id, sha256}` in that same PAUSED graph. Omission requests no image generation or upload. The plan freezes actual Material integrity receipts, deduplicates shared uploads and attaches only durable provider-confirmed string hashes; readback checks the full text arrays and actual image bindings/metadata. Creation remains separate from moderation and paid delivery.

Follow [the complete launch recipe](campaign-launch.md) for offer → supported SEARCH material → actual PAUSED creation/readback → separate moderation and finite launch → saved observation. Native `create_campaign` freezes a finite budget with verified VAT. The current `direct_custom_period` supports one to ninety days without a mandatory percentage reserve; PAUSED creation accepts explicit unknown funding and future start dates. Paid launch has its own current funding checks.

### Campaign schedule, demographics and archive

`keyword_bid` prepares an exact existing phrase's fixed SEARCH bid on a PAUSED `UNIFIED_CAMPAIGN` using `HIGHEST_POSITION` with Network `SERVING_OFF`. Use the selected native group membership, its actual phrase and current campaign version; the owner resolves a unique native KeywordId from its fresh graph. A separate bid-only plan has no `money_policy`, funding prerequisite, budget update or delivery action. Reuse applicable user authorization. `bid_rub` is the native bid in RUB excluding VAT; the writer multiplies it by 1,000,000 without a VAT conversion. Actual `KeywordBids.get` before/readback and current currency bounds prove the setting; changing bids does not prove a traffic result, a guaranteed paid CPC or a spending cap. Active campaigns, automatic strategies, manual NETWORK, mixed placement and autotargeting are outside this preparation profile. Read an interrupted Application before further action; external resume cannot be atomically excluded by Direct's bid API, so changed campaign state leaves preparation unproven.

Provider contracts: [fixed bids](https://yandex.ru/dev/direct/doc/ru/keywordbids/set), [native bid readback](https://yandex.ru/dev/direct/doc/ru/keywordbids/get), [current currency bounds](https://yandex.ru/dev/direct/doc/ru/dictionaries/get), [VAT basis](https://yandex.ru/support/direct/ru/payments/faq).

`campaign_schedule` changes the selected campaign as a whole: seven `days` rows, each with `day=1..7` and 24 exact `coefficients=0..200` in steps of ten; zero stops serving for that hour. At least eight serving hours per week are required. Omit `timezone` to preserve the campaign's current time zone; set it only when the selected change requires another provider-supported IANA zone. Read the current zone yourself, rather than asking the user to find its identifier. `consider_working_weekends` and `suspend_on_holidays` make the calendar explicit. The older `group_settings.schedule` cannot set a group-specific calendar. Schedule local hours and Direct's Moscow report/budget dates have different calendars.

`segment_adjustment.segment_id` accepts `mobile` or `demographic:<gender>:<age>`, where gender is `male`, `female` or `any`, and age is `0_17`, `18_24`, `25_34`, `35_44`, `45_54`, `55` or `any`. Both parts cannot be `any`; coefficients are `percent=0..1300`. The writer preserves other slices, rejects overlap and ambiguous/disabled existing slices, and verifies actual coefficients. Unsupported legacy age buckets need a separate correction rather than guessed equivalence.

`archive_campaign` is a separate plan for an already PAUSED campaign. Apply `delivery(state="PAUSED")` first if stopping is authorized and needed, then use its current state/version for archive. Provider funds and eligibility restrictions still apply. Archive retains IDs/statistics and does not prove that a transfer, deletion or full provider change-history reader exists.

### Retargeting windows and exclusions

`retargeting` creates a goal-based Direct condition and attaches its confirmed ID to one existing group. Use a selected native scope containing that exact group and `get_native_configuration(family="ad_groups", operation="retargeting")`. Its current objects expose `targeting` and `audience_targets` from the same observation as the returned version. The campaign must be PAUSED, NETWORK and on a supported automatic strategy. By default, `OfferRetargeting=NO`, no alternative active keywords/autotargeting and no existing audience target keep the condition's exclusion meaningful. The operation never starts delivery.

For an ordinary Creator group, `replace_group_targeting=true` explicitly converts the selected group: the frozen current keyword/autotargeting IDs are suspended and offer retargeting is disabled before attachment. Show these exact removals with the selected audience and reuse only authorization covering them. Other groups and ads are preserved; campaign delivery stays paused. No existing AudienceTarget is silently deleted or replaced. An interrupted conversion may leave some criteria stopped and no final attachment, so inspect the original Application and per-step readback before further work.

Read `get_operations_catalog(operation="retargeting", include_schema=true)`. Supply `group_id`, `name`, optional `description`, `strategy_priority=LOW|NORMAL|HIGH` and `rules`. Each rule has `operator=ALL|ANY|NONE` and `goals=[{counter_id, goal_id, days}]`, with a window of 1..540 days. All rules apply together; `NONE` excludes recent achievers. At least one ALL/ANY inclusion is required. Each actual counter/goal needs the existing current measurement owner proof; use supported measurement discovery/scope selection when missing. This path supports ordinary event goals accepted by that owner. Metrika retargeting-only definitions, arbitrary audience segment IDs or technical strategy sentinels are outside this operation.

For example, an evidenced event in the last 30 days with the same event excluded for 7 days uses ANY(window=30) and NONE(window=7). This describes an authored audience condition; it does not prove audience size or future performance. Preserve the original audience material, event definition, windows and exclusion reason through the exact Plan/Application.

After confirmed condition creation, the writer rereads its real availability, rules, scope and allowed group types before attachment. Direct may reuse a condition with identical rules and keep its old name/description. Readback proves the returned condition ID, target ID, group, priority and exact windows/exclusions. An incompatible provider group leaves the attachment unapplied and retains the original result for recovery; unknown creation never authorizes another add. Account-wide condition deletion, arbitrary segments, and attachment to an unproved group type remain unsupported.

Provider contracts: [condition creation](https://yandex.ru/dev/direct/doc/ru/retargetinglists/add), [condition applicability](https://yandex.ru/dev/direct/doc/ru/retargetinglists/get), [audience attachment](https://yandex.ru/dev/direct/doc/ru/audiencetargets/add). The returned `AvailableForTargetsInAdGroupTypes` is authoritative for the actual group; a service being available does not make every group type applicable.

### Upload and attach selected ad images

For an existing supported `ResponsiveAd`, `ad_update.patch.images` accepts up to five exact `{material_id, sha256}` references. Use the selected immutable image Material and its actual `get_material` receipt. A local file can enter the existing `prepare_material_upload` path; then retain its returned material ID/hash. This profile accepts PNG/JPEG image Materials within the existing 8 MiB material limit. Do not put binary/base64 into an operation proposal, substitute a local path or infer an upload from an image URL.

Use selected native ad membership and `get_native_configuration(family="ads", operation="ad_update")` for exact current ad content/version. Preserve the selected titles/texts, URL and landing source. `images=[]` removes the selected ad's image bindings; omission preserves them. Old shared images and unselected ads are retained. The existing plan shows the exact material/project/hash/length and ad changes; the backend reads the actual bytes under current access, uploads once, then binds only the provider-confirmed string `AdImageHash`. It checks real image type/applicability and the current ad before update, and verifies the actual hashes and image metadata afterwards.

New PAUSED Creator ads can include the same selected Materials directly through `ads[].images`; use `ad_update.patch.images` for a later change to existing ad IDs. `copy.image_ref` remains unsupported and is not an image upload reference. An image upload or attachment does not prove accepted moderation, actual rendering or delivery. Prepare image content when requested and supported, reuse the selected version and its authorization, and keep moderation/launch as their actual separate operations.

A lost upload reply leaves an unresolved asset identity. Recover the original Plan/Application through the existing journal/readers; never repeat the add, infer a hash from a name or create a replacement command just because an image looks unchanged. Unsupported image types, current ad drift or lost access prevent attachment and leave the actual partial state visible. Provider contracts: [image upload](https://yandex.ru/dev/direct/doc/ru/adimages/add), [image metadata](https://yandex.ru/dev/direct/doc/ru/adimages/get), [ResponsiveAd image bindings](https://yandex.ru/dev/direct/doc/ru/ads/update).

### Create a feed-driven product ad

Use `prepare_site_feed` with the actual public YML feed `source_url` for regularly updated product data, or with `source_material_id` for a one-time file. If given a website, inspect its supported public page/link readers to find the actual catalog link; do not guess a feed endpoint or ask for technical IDs. The reader verifies the public source and retains its exact immutable sample within the existing 1 MiB/5,000-offer simple-goods profile. An inaccessible, unsupported or invalid source gives its actual error or corrections needed upstream. A URL sample cannot apply local `utm` rewrites; keep `remove_utm_tags=false` to preserve tracking unless removing upstream UTM was explicitly selected. The native `shopping_ad` profile consumes the selected valid `feed={publication_id,fingerprint}` for `simple_goods.1`, YML, RETAIL. A sample/download proves no native creation; prices and URLs have not been compared to the live site.

Select the existing PAUSED campaign and exact ЕПК group through native membership, then read `get_native_configuration(family="ad_groups", operation="shopping_ad")`. Its current version/data include the group's actual targeting and ads. Read `get_operations_catalog(operation="shopping_ad", include_schema=true)` and supply `campaign_id`, `expected_version`, `group_id`, `feed`, feed `name` and one `default_text`. Prepare that name/text from the actual offer/catalog. Optional `title_sources`/`text_sources` select supported feed fields when useful; omission uses actual provider defaults, retained as native observations rather than invented frozen copy. The agent resolves suitable sources from the feed and does not ask the client for a technical mapping. The slot must have no non-archived ShoppingAd/ListingAd; other ads and targeting are retained. For a new campaign, finish its supported PAUSED creation first and use the returned real group identity for this separate product-ad step.

The exact Plan uses `Feeds.add(URL, UrlFeed={Url,RemoveUtmTags})` for a public-source publication and `Feeds.add(FILE)` for a material. Direct's robot refreshes the URL feed usually daily, possibly less often for large sources; no client scheduler or file re-upload is needed. SiteFeed remains an immutable earlier sample, while the provider feed is live. The worker waits for actual `DONE` processing and available text-source names, creates `ShoppingAd` with that confirmed `FeedId` and `GenerationScopes=["OFFER"]`, then suspends the new ad. Binary data stays out of the model-facing proposal/receipt. Feed processing and ad generation are separate asynchronous stages: `native_feed_processing_pending` or `native_shopping_generation_pending` keeps the original Application pending. Read that same Application; the worker can continue only its proven unsent step after current authority, campaign, group and targeting checks. It never repeats an uncertain feed/ad add. Lost identities, native errors, changed source URL/options or definitions, and expired authority retain the actual recovery state.

Only the exact confirmed feed/ad IDs, PAUSED campaign/ad and real `FeedProcessingStatus=PROCESSED` establish creation. Native readback retains source URL/options, processing, `UpdatedAt` and `NumberOfItems`; normal URL refresh can change the latter without invalidating the original graph. These metadata do not compare individual current prices, stock or product links to the earlier XML, prove rendered coverage, or establish accepted moderation. Return the real status and next requested step: wait for the same Application, correct the upstream source after an error, or proceed to separately authorized moderation/delivery. Generation must be ready before activation; accepted moderation, exact finite money policy, current funding and execution authority still apply. Other business profiles, LISTING generation and product-filter editing remain unsupported. Existing `shopping_feed_update` only replaces an exclusively used FILE feed; it does not edit a live URL source or a shared feed.

Provider contracts: [native URL/file feed creation](https://yandex.ru/dev/direct/doc/ru/feeds/add), [URL refresh schedule](https://yandex.com/support/direct/en/feeds/add), [processing and text-source catalog](https://yandex.ru/dev/direct/doc/ru/feeds/get), [ShoppingAd creation](https://yandex.ru/dev/direct/doc/ru/ads/add), [generation readback](https://yandex.ru/dev/direct/doc/ru/ads/get).

### Update an existing product feed once

Prepare or select the exact corrected YML publication through the same feed owner. For current prices, availability or product links, use the actual supplied catalog and preserve the other selected product data; do not invent replacements. Read the selected PAUSED group's `get_native_configuration(family="ad_groups", operation="shopping_ad")`, including its `shopping_ads` and `shopping_feeds`. `shopping_feed_update` takes the actual `group_id`, native integer ShoppingAd `ad_id`, campaign `expected_version` and `feed={publication_id,fingerprint}`. Read its catalog schema if needed. The writer retains FeedId/ad ID, existing ad copy/selectors and feed name, replacing only the FILE content/filename. The current feed must be RETAIL, processed and used exclusively by that selected PAUSED ad; an unselected shared consumer prevents this operation because its data would also change.

Freeze and execute the exact replacement through the existing Plan/Application. `Feeds.update` is sent once with owner-verified bytes. Reuse that same Application during `native_feed_processing_pending` or `native_shopping_generation_pending`; no second upload is needed. A definite exact update receipt, a changed native feed revision with DONE and observed PROCESSED generation establish the supported technical result. [Feeds.get](https://yandex.ru/dev/direct/doc/ru/feeds/get) does not return provider file bytes, individual prices, stock or product URLs, so report those limits and the observed stages instead of claiming item-by-item verification or actual delivery. A lost [Feeds.update](https://yandex.ru/dev/direct/doc/ru/feeds/update) reply remains unresolved even if metadata looks plausible; never repeat it or submit a replacement command to bypass recovery. This is one-time replacement, not regular synchronization.
