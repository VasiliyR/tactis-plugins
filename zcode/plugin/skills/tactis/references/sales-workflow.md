# Sales: обращения до оплаченной продажи

Read [the implemented platform route](platform-workflow.md#7-crm-calltracking-and-offline-conversions) for the corresponding exact tools and retained artifact/effect boundaries.

Use this procedure for the linked Sales cycle: inquiry quality, processing gaps, one useful assignment, its execution report, paid outcomes and return. Start with “Где обращения теряются до продажи и что сделать первым?” or resume the client's existing check. The connected source reads paginated deal/payment observations and, when requested, native stage and activity histories. Unsupported quality definitions and unproved human-response timestamps remain unknown. A private inquiry CSV supports elapsed response SLA through the separate route below. Human-confirmed CRM aggregates remain a supported partial source. Author interpretations externally; current status/payment observations do not prove causes.

Complete the task through Work `task_resolution="complete"` only when its requested result is actually delivered, retain its committed saved receipt; read the exact task only when its current status matters. A saved cross-product draft is not task completion. Prose locators do not become typed evidence or external execution receipts.

## When data is missing

If there is no usable publication, give the available finding and a specific first assignment instead of an empty funnel or generic advice. For example:

> Пока нет подтверждённых CRM итогов: по событиям сайта нельзя сказать, сколько обращений дошло до оплаты. Первое задание владельцу продаж — подготовить обезличенные итоги одной когорты обращений: период их создания, дату среза, число обращений, открытых, закрытых без оплаты, оплаченных и неразобранных; пояснить статусы и исключения. Это позволит отделить ожидание от закрытых обращений и выбрать следующую проверку. Готовность — все обращения учтены без пересечений, определения и дата среза указаны; персональные строки сюда не нужны.

Ask only for the material missing definition or this bounded aggregate. User-provided totals remain attributed information, not a human-confirmed CRM publication. If an import exists but is partial, show its useful known groups and request only the missing coverage/meaning. For “на какой стадии/сколько дней” explain the additional minimum: defined stages, same-cohort counts reaching each stage, open remainder/closed reasons, status cutoff and first-response/transition-time distributions from the business's own CRM. Current CSV does not retain these fields; preparation of those aggregates is a task, not an implemented stage reader. Do not request personal records or label missing durations as zero.

## Save and return to the exact result

For requested persistence or a result that needs continuation, use the current `record_work_session` schema with kind `assessment`, a bounded summary, limitations and next_step containing the complete assignment. Store the selected account, source/cohort, CRM locator (id/version/digest), meaning of statuses/date, known cutoff, exclusions, attributed answers and proposed or agreed completion condition. Ordinary analysis saving needs no separate approval. Keep unnecessary personal data and transcripts out of Work.

CRM locators in prose are **not typed evidence**. Use a supported `crm_source` evidence reference only when that actual schema/catalog exposes it, with the exact connected-source publication/account/digest. Human-import CRM IDs are not interchangeable with `crm_source`. Do not put unsupported CRM IDs into foundation refs or attach the versioned `assessment` payload without its required actual A1 basis. Server validation of ordinary Work does not mechanically validate CRM numbers in its summary.

Follow [durable continuation](durable-continuation.md) for saving/recovery and conflicts rather than inventing a second persistence protocol. When actual confirmed context versions and a schema-supported basis or meaningful revisit condition are available, prefer the supported continuation.mode="delta" on that exact head. A conclusion without a typed basis requires explicit uncertainty, limitations and a real supported revisit time/event. Never invent a date, goal, A1 or event enum to admit a head. Otherwise save ordinary Work; it does not advance the current head. A committed saved receipt confirms the stored assignment; read exact Work for history, conflicts or recovery. Unresolved writes remain unconfirmed, failed writes unsaved.

On return, read the relevant exact Work as well as the full current summary when available; an ordinary newer Work may be the useful result. Resolve the saved source kind: connected source via `get_crm_source_publication`, legacy human import via `get_crm_publications`. Compare selected source/account/scope/mapping/version before repeating a numerical conclusion. Corrections become new evidence, not a rewrite of old Work. If a legacy version is outside the bounded list, keep its historical locator but do not claim it has just been checked. A forbidden source read cannot be bypassed with saved private text; an outage leaves current source verification unknown.

Ask for the assignment's result only if it is still missing. Distinguish an attributed completion report, a newly confirmed aggregate and remaining unknowns; save the useful update and one next step. Prepared text, its execution and an increase in paid sales are different outcomes. This reference does not prove causal uplift or run Sales reasoning while the host is closed.
