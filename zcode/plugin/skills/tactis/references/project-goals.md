# Цели и числовые показатели проекта

Перед решением, которое меняет приоритеты, бюджет или критерий успеха, используй `project_goals` из brief и прочитай `get_project_goals`. При сокращённом preview нужен полный read. Прогресс читается через `get_project_goal_progress`; новый расчёт по уже сохранённым данным — `capture_project_goal_progress`. Чтение сохранённых целей не требует Директа.

## Из слов пользователя в общую модель

Сохрани исходную формулировку в `original_text`. Отдельно задай период с годом, timezone и задержкой конверсий, приоритет, ответственного и охват. Числа разделяются на:

- `targets`: результат, к которому стремимся;
- `constraints`: границы, которые нельзя нарушать ради результата;
- `parameters`: сообщённые значения, оценки и предположения бизнеса с происхождением, валютой и горизонтом LTV;
- `bindings`: точные источники наблюдаемых фактов и их определения.

Пример: «100 квалифицированных заявок за ноябрь, стоимость до 1 500 ₽, расходы до 150 000 ₽» → `mql >= 100`, `cpql <= 1500 RUB`, `ad_spend <= 150000 RUB`. Уточни год и смысл квалификации, если они неизвестны. CPA технического события и CPQL различаются. Не исправляй неоднозначные суммы или порядок нулей молча. Если пользователь назвал 15 000 и 150 000 для одной границы, сохрани противоречие как требующее уточнения.

Метрика выбирается из `get_metric_catalog` с пагинацией; знание кода не означает наличие данных. Для относительного изменения нужен точный `baseline_observation_id`, сопоставимые определения, охват, длительность окон и зрелое базовое наблюдение. Не задавай произвольную исполняемую формулу.

Используй существующий путь `propose_context_bundle` → `apply_context_bundle` → `get_project_goals` / business-context readback. Передай полный типизированный `project_goals` рядом с сохранёнными memory/goal и их текущими версиями. Сохраняй существующие ID целей, увеличивай `revision` изменённой цели на один. Для прекращения цели ставь `archived`; не удаляй действующую цель из списка. Правка цели и параметров создаёт общую версию контекста с CAS. Указание пользователя сохранить цель уже разрешает этот путь. Недостающую интерпретацию не выдавай за подтверждённую цель.

`business_goal` — короткое текстовое представление тех же целей. Не создавай вторую числовую модель в произвольных ключах памяти. Старые текстовые поля сохраняют совместимость; при расхождении со структурированной целью требуется уточнение.

## Связать с реальностью

`list_project_metric_sources` показывает сохранённые импорты, CRM/calltracking и ручные факты с периодом и доступными полями. Native Direct выбирается существующими Daygrain readers. Для conversions укажи точную counter/goal пару и conversion_source=direct либо metrika; смена события не должна молча менять смысл показателя. Для обновляемого CRM binding закрепи source_definition_version из выбранной публикации. Закрепи точную публикацию либо разрешённую связь с подключением для следующих наблюдений. Поле источника должно иметь то же бизнес-значение, что выбранная метрика. Цель Метрики описывает событие измерения; её counter/goal ID входит в связь и не заменяет бизнес-цель проекта.

Ручной факт сохраняется через `record_project_metric_facts` с периодом, охватом и происхождением. Оценка остаётся оценкой. `parameters` никогда не подменяют фактические заявки, расходы или выручку. Общий показатель проекта нельзя молча заменить одним аккаунтом. Для суммы нескольких источников нужны совместимые определения, отсутствие пересечений и явное основание `sum_disjoint`. Повторные версии одного источника не складываются. Общий коэффициент из разных систем требует согласованного `comparison_basis`; факт загрузки конверсии не доказывает атрибуцию или квалификацию.

Ноль, отсутствие данных, неполное покрытие и несовместимые окна различаются. Недоступный LTV не равен нулю. Успешная сделка не равна оплате; paid cohort по дате создания не равен оплатам за период. При неизвестном качестве заявок CPQL остаётся неизвестным. Не считай все 155 метрик автоматически подключёнными.

## Решения, DAG и обратная связь

Сначала соблюдай ограничения; среди допустимых вариантов ориентируйся на приоритетные цели. Явное противоречие передай пользователю. Назови, на какую цель направлено решение, её версию, числовую гипотезу и способ проверки. Плановый результат остаётся прогнозом. Сохранённый медиаплан содержит контекст целей и проверки сопоставимого лимита расходов; этот лимит не разрешает расходовать деньги или менять рекламу.

Фоновый data worker рассчитывает конечные наблюдения и создаёт `project_goal_review`. Он не вызывает LLM и не меняет рекламу. Прочитай точное наблюдение из задачи, проверь текущую цель и запиши вывод в Work с `platform_refs.kind=project_goal_observation`. Без этой ссылки задачу закрыть нельзя. При изменении смысла цели перепроверь продолжение; исторические наблюдения и отчёты сохраняют исходный смысл.

Если пользователь попросил отчёт, после записи проверенного Work используй `create_project_goal_report` с этим Work и наблюдением. Отчёт доступен обычным private HTML/PDF и библиотечным путём. Не генерируй документ только ради записи памяти. Храни наблюдение, решение, действие и последующую проверку как раздельные основания. Последовательность чисел сама по себе не доказывает причинный эффект и не запускает автоматическое обучение модели.
